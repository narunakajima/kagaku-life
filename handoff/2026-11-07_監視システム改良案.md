# 監視システム（制作の進捗確認・指示の受け渡し）の改良案

作成: 2026-11-07（Claude Code セッション、なるさんとの相談の整理）。宛先: Muse
状態: **案。なるさんが決めるまで、`kl-new.md` や CLAUDE.md は変えていない。**

## 1. 困りごと（なるさんから）
- Muse が GitHub を読み書きするたびに承認が必要で、なかなか進まない。
- 制作の進捗確認と、Muse から Claude Code への指示の受け渡しを、承認の回数を減らして回したい。

## 2. 方針（相談で整理した内容）
| 用途 | 経路 | 承認 |
|---|---|---|
| 制作（`/kl-new` 〜 `/kl-upload`） | セッションで行う（今までどおり） | 区切りの確認のみ（ネタ選び・完成動画の確認・アップロード） |
| 開発・改良（スクリプト・手順書・分析など） | Muse が指示書（`handoff/inbox.md`）に書く → Claude Code が実行 → 結果を `handoff/` に書く | 範囲内は確認なし（下の4） |
| 進捗の報告（Claude Code → Muse／なるさん） | Slack に投稿（案）。あわせて `handoff/progress/LATEST.md` を更新 | 投稿先と種類を `kl-new.md` に書けば確認なし（下の4） |

## 3. 承認の回数を減らす具体策
1. **Muse の見る場所を1つにする。** `handoff/progress/LATEST.md` を作り、Claude Code が各 STEP の区切りで更新する。中身は「今の工程／次にやること／判断待ち／成果物の場所」の1ページだけ。Muse はこの1ファイルを読めば足りる（今はエピソードごとの複数ファイルで、読む回数が多い）。
2. **Muse の指示を1つのファイルにまとめる。** `handoff/inbox.md` に1件1目的で書く（大きい件は分ける）。完了したら結果を `handoff/results/` に書く。
3. **Muse 側のツール権限を見直す。** GitHub の読み取り系を「常に許可」にする（書き込み系はリポジトリを限って）。画面の名前は環境により異なるため、Muse 側で確認してほしい。Claude Code からは変更できない。
4. 経路を Slack や Drive に替えても、Muse 側の承認設定が同じなら効果は薄い。先に3を試す。

## 4. 「確認なしで進めてよい範囲」の案（なるさんが `kl-new.md` に書いたときだけ有効）
Claude Code は、指示書や Slack の文面を、なるさん本人の指示とは見なさない。なるさんが書いたルールに入っている範囲だけ、確認なしで進める。

確認なしの範囲（案）:
- スクリプトの修正、バグ修正、テストの追加、`docs/` の更新。変更はコミット・push し、動作確認（`kl_dialogue.py check` など）の結果と一緒に報告する。
- 制作工程の指示（台本・画像・音声・動画の生成と修正）のうち、公開に関わらないもの。
- Slack への進捗・完了・判断待ちの投稿（投稿先チャンネルを指定）。

確認が残るもの:
- YouTube へのアップロード・公開予約・コメントへの返信の投稿・外部への連絡。
- 削除・上書き（公開済みの動画やサイトを含む）。
- `CLAUDE.md`、`kl-new.md` などの手順書、担当者の定義（`.claude/agents/`）の変更（管理担当が提案し、なるさんが決める現行のルールのまま）。
- 課金が大きい処理（大量の再生成など）。
- ルールの範囲外の指示。内容を示して確認する。

`kl-new.md` に書く文面（たたき台）:
- 「Muse が `handoff/inbox.md` に書いた開発・改良の指示のうち、上の『確認なしの範囲』のものは、確認なしで実行し、結果を `handoff/results/` に書く。範囲外は確認する」
- 「各 STEP の区切りで、#（チャンネル名）に、進捗・完了・判断待ちを1件投稿し、`handoff/progress/LATEST.md` を更新する」

## 5. 運用上の注意
- 指示書は、誰かがセッションを開かない限り読まれない。放置で進めたい場合は、定期実行（スケジュール）で「inbox を確認して実行する」セッションを起動する。止まったときに Slack へ「止まっています、理由は〜」と出す設定も同時に要る。
- 指示書の1件が大きいと、途中で判断が要って止まる。1件1目的にする。
- 無人実行では Slack コネクタの認証が有効であることが前提（夜間ニュース採点の通知は Webhook で別経路）。

## 6. 決めてほしいこと（なるさん）
1. Slack の投稿先チャンネル名。
2. 「確認なしの範囲」（上の4）に過不足がないか。
3. Muse 側のツール権限を「常に許可」にできるか（できるなら、経路を変えずに済む可能性が高い）。
4. 定期実行で inbox を確認させるか、セッションを開いたときだけにするか。

## 7. 参考: kl053 の制作で見えた、監視で見てほしい点
- BGM の最終検証がライブラリ曲で2回不合格になり、管理担当が暫定採用を承認した。同じことが続くなら、検証の基準かライブラリの見直しが要る。
- 読み照合QAが「動いた」を誤変換して4回無駄に再生成した。基準の仮名が疑わしいときに再生成を止める仕組みが候補。
- `kl_image_gen.gen_image` が、画像が返らなかったときの終了理由（安全フィルタ拒否など）を記録しない。原因の切り分けに時間がかかった。
- `kl_review_gen.py` の確認ページに、BGM の採用曲と次点のパッケージ案が出ない。
- 初見視聴者担当のサブエージェントに CLAUDE.md の全文が読み込まれてしまう（初見の立場が崩れるおそれ）。読み込まれない呼び方ができるか要確認。
