# KLチーム（幸せな未来のサイエンス（kagaku-life）制作チーム）— 担当者制（2026-10-27〜）

主要な工程を**専任の担当者（サブエージェント）**に固定し、毎回同じ担当者を呼ぶ。担当者は自分のノートで
前回までの教訓と管理担当のフィードバックを引き継ぐ。毎月、管理担当がアナリティクスと作業記録から
各担当の貢献を評価し、フィードバックを返す。samurai-chronicles・lamp-whisper も同じ仕組み（各リポジトリの `team/TEAM.md`）。

## チームの目標

1. **視聴者の獲得** — 新しい視聴者に見つけてもらい、見てもらう
   - 指標: 公開後14日のインプレッション・CTR、再生数、登録者の純増（KL は `subscribed_status` が使えないので新規視聴者の比率は見ない）
2. **高評価の獲得** — 見た人に「良かった」と思ってもらう
   - 指標: 高評価数・高評価率（高評価 ÷ 再生）、平均維持率・視聴時間、コメント数

想定する視聴者は CLAUDE.md「想定する視聴者」。本編と Shorts は分けて見る。

## 改善のサイクル（PDCA）

毎月、次の輪を1周させる。輪をつなぐのは「改善アクション」（管理担当が出す、担当ごとの具体的な行動。ID 付き、1人2件まで）。

| 段階 | 誰が | 何をする | 使うもの |
|---|---|---|---|
| Check（アナリティクス） | 管理担当 | 月次の `/kl-analytics` で数字を集め、前回までの改善アクションが効いたかを判定する | 集計、`team_stats.py`、`team_log.py summary`（適用した回・適用率） |
| 評価 | 管理担当 | 担当ごとに成果・品質・改善を採点する | `team_log.py score` |
| Act（フィードバック） | 管理担当 | 次に効きそうな行動を改善アクションとして登録し、ノートに書き出す | `team_log.py action add`、`sync-notebooks` |
| Do（行動の改善） | 各担当 | 作業の最初にノートの改善アクションを読んで必ず実行し、適用した回を記録する | `team_log.py applied`、担当メモ |
| （記録） | 進行担当（メイン） | 呼び出しの結果と、指摘の原文を記録する。自分の進行も記録し、評価を受ける | `team_log.py add`・`feedback` |

- **効果の判定は、適用した回の測定窓（公開後14日）がそろってから。** 制作から公開・測定まで時間がかかるので、
  あるアクションの判定は、出した月の翌月か翌々月の評価になることが多い。それまでは「判定待ち」で続ける
- 判定の結果: 効果あり → ノートの「続けている教訓」へ。2か月続けて効いたら CLAUDE.md・手順書への昇格を提案（ユーザーが承認）。
  効果なし・取り下げ → 閉じて、別のアクションを考える
- 月次評価を忘れないよう、制作コマンドの STEP 0 で `python3 team_log.py due` が前月の評価の有無を確かめる（済んでいなければ一言知らせる）

## 名簿

名簿の正本は `.claude/agents/*.md`（`python3 team_log.py roster` で一覧）。
**担当者は「KLチーム ○○担当 名前（カタカナ）」の形で呼ぶ**（例: 「KLチーム 脚本担当 ライアン」）。会話・報告・評価・記録の表示はこの形にそろえる。
`Agent` の `subagent_type` と作業記録には呼び出し名（`kl-writer` など）を使う。`team_log.py` の `--agent` には名前（カタカナ）も書ける。

| チーム 担当 名前 | 呼び出し名 | モデル | 担当する工程 | 主に責任を持つ指標 |
|---|---|---|---|---|
| KLチーム 管理担当 ケビン | `kl-manager` | Opus | 月次のアナリティクスと評価・フィードバック（`/kl-analytics`）、チームの取りまとめ、エスカレーションの受け手（下記） | チーム全体の2目標 |
| KLチーム 進行担当 ダニエル | `kl-coordinator`（メインの会話） | メイン（通常 Sonnet） | 制作コマンドの進行、担当者の呼び出し、担当のいない工程、記録（定義は `team/coordinator.md`） | 進行への指摘ゼロ・記録漏れゼロ・エスカレーションの遅れゼロ |
| KLチーム 企画担当 ミア | `kl-planner` | Opus | `/kl-new` STEP 1 のベスト3の仕上げ（ケースC 手順2〜5、ケースB の選定） | 14日インプレッション・CTR・再生数 |
| KLチーム 脚本担当 ライアン | `kl-writer` | Opus | STEP 2 の台本（`script_prep/`・エピソードJSON）、STEP 5.5 の指摘を受けた直し | 平均維持率・視聴時間・高評価率 |
| KLチーム 台本レビュー担当 グレース | `kl-script-reviewer` | Opus | STEP 5 の面白さ・品質レビューと直接修正 | 平均維持率・高評価率・制作者の台本への指摘ゼロ |
| KLチーム 初見視聴者担当 エマ | `kl-first-viewer` | Opus | STEP 5.5 の初見レビュー（資料を見ない） | 制作者の「意味が分からない」系の指摘ゼロ |
| KLチーム 映像担当 レオ | `kl-art-director` | Opus | STEP 6.5 の図・資料カードの可読性、STEP 6.7 のクロスシーン一貫性、画像のエスカレーション | 画像の作り直し・画像の指摘ゼロ、維持率 |
| KLチーム コミュニティ担当 クロエ | `kl-community` | Sonnet | `/kl-upload` STEP 3.6 のコメント返信の文面 | コメント数・返信率・高評価率 |

担当のいない工程（ニュースの収集・採点、ファクトチェック STEP 4、画像生成・TTS・BGM・動画生成などのスクリプト実行、サムネイル）は、KLチーム 進行担当 ダニエル（メインの会話）が行う。
担当を新設・統合したいときは、管理担当が月次評価で提案し、ユーザーが決める。

## 呼び出しのルール

- 上の工程では、`Agent` の `subagent_type` に**担当名**を指定する（`general-purpose` を使わない）。`model` も担当の定義と同じ値を明示する
  （呼び出し側の `model` は担当の定義より優先されるので、違う値を書かない）
- 依頼文（プロンプト）には、これまでどおり手順書の指定どおりの内容を書く。担当者は会話の経緯を持たない
- 担当者は作業の最初に `team/notebooks/{担当名}.md` を読む（担当の定義に書いてある）。ノートは CLAUDE.md・手順書より下位で、
  食い違ったら CLAUDE.md・手順書に従い、食い違いを報告する
- 同じ工程を同じ回でやり直すときも、同じ担当を呼ぶ

## 記録（KLチーム 進行担当 ダニエルが行う）

担当者の呼び出しが終わるたびに、結果を1行記録する。呼び出しの回数は SubagentStop フックが自動で記録するが（`.claude/settings.json`）、
結果（一発で通ったか・やり直したか）はメインにしか分からないので、手動の記録が評価の材料になる。

```bash
python3 team_log.py add --agent kl-writer --episode kl{NNN} --step 2 --result ok
#   --result: ok（一発で通った）/ retry（同じ担当にやり直させた）/ fail（失敗した）/ escalated（他の担当・管理担当に引き継いだ）
#   --retries N（やり直しの回数）、--note "短いメモ"
```

**成果物への指摘も記録する。** なるさんの指摘・QA の不合格（ファクトチェックの high_risk、`check` の ❌、初見レビューの【致命的】）・視聴者のコメント（誤りの指摘など）を受けたら、その成果物を作った担当に付ける。
指摘は原文のまま書く。

```bash
python3 team_log.py feedback --agent kl-writer --episode kl{NNN} --source user --severity major --text "指摘の原文"
#   --source: user / qa / viewer / manager、--severity: major（作り直しが要る）/ minor
```

**改善アクションの適用は、担当が自分で記録する**（`team_log.py applied`。担当の定義の手順3）。Bash を使えない担当
（KLチーム 初見視聴者担当 エマ）の分は、メインが担当メモを見て記録する。メインは担当メモに「適用した改善アクション」が無いのに
実施中のアクションがある担当に気づいたら、その場で担当に確かめる。

どの担当の成果物か迷ったら、その指摘を防げた最初の工程の担当に付ける（例: 台詞の「意味が分からない」→ KLチーム 脚本担当 ライアン（`kl-writer`） に付け、
初見レビューが見落としていたら KLチーム 初見視聴者担当 エマ（`kl-first-viewer`） にも付ける。図のラベルの誤り → KLチーム 映像担当 レオ（`kl-art-director`））。
初見レビューの【致命的】は、レビューした KLチーム 初見視聴者担当 エマ（`kl-first-viewer`） ではなく、書いた KLチーム 脚本担当 ライアン（`kl-writer`） への指摘として記録する（見つけたのは手柄）。担当のいない工程や、進行（呼び忘れ・手順の飛ばし・記録漏れ）への指摘は KLチーム 進行担当 ダニエル（`kl-coordinator`）に付ける。

## エスカレーション

CLAUDE.md「モデルの使い分けとOpusへのエスカレーション」の条件に当たったときの引き継ぎ先:
- 画像（同じシーンの CRITICAL が直らない、図の可読性）→ KLチーム 映像担当 レオ（`kl-art-director`）
- 台本（`check` の ❌ が直らない、ファクトチェックの high_risk が残る）→ KLチーム 脚本担当 ライアン（`kl-writer`）
- それ以外（スクリプトの失敗、原因の分からない不具合、担当をまたぐ問題）→ KLチーム 管理担当 ケビン（`kl-manager`）
- BGM は例外（CLAUDE.md のとおり、2回不合格ならライブラリの曲に切り替える。引き継がない）

引き継いだら、元の担当の記録を `--result escalated` にする。

## 月次評価（管理担当）

**毎月第3月曜に、`/kl-analytics` の STEP 4 で前月分を評価する**（日程の正本は `team/schedule.json`）。

材料:
- アナリティクスの集計（`kl_analytics_report.py`）
- 高評価・コメント数（`/usr/bin/python3 team_stats.py --since {前月1日}`）
- 作業記録の集計（`python3 team_log.py summary --month YYYY-MM`）と、前月の評価・各担当のノート

評価の付け方（担当ごと）:

| 軸 | 見るもの | 点 |
|---|---|---|
| 成果 | 担当が責任を持つ指標（名簿の表）。同じ月の中央値・前月と比べる | 1〜5（データ不足なら `-`） |
| 品質 | 一発OK率、やり直し・引き継ぎの回数、指摘（重）の数 | 1〜5 |
| 改善 | 前月の改善アクションの適用率（機会のうち何回使ったか）と、その効果 | 1〜5（初回は `-`） |
| 総合 | 上の3つと、チームの目標への貢献 | S / A / B / C / D |

- **少ない本数の差を貢献と決めつけない。** 再生・高評価は企画・脚本・画像・公開時期の合作で、1つの担当に分けられない。
  `/kl-analytics` の注意（実数を併記、`MIN_CATEGORY_N` 未満は参考程度）を守り、成果が判定できない月は `-` にして、品質と改善で評価する
- 評価は `team/evaluations/YYYY-MM.md` に書き、点は `python3 team_log.py score ...` で `team/scorecards.jsonl` に残す
- 前回までの改善アクションを判定して閉じ（`team_log.py action close`）、新しい改善アクションを登録して（`action add`）、`sync-notebooks` でノートに書き出す
- 各担当のノートの「管理担当からのフィードバック」を書き換える（行動に落とせない所感。具体的な回と箇所を挙げる）
- **管理担当が自分で変えてよいのはノートと評価の記録だけ。** CLAUDE.md・手順書・担当の定義（`.claude/agents/`）の変更は提案にとどめ、
  ユーザーの承認を取ってから反映する（`/kl-analytics` STEP 5〜6）
- 総合 D が2か月続いた担当は、担当の定義・依頼文・モデルの見直し案を出す

## ノート（`team/notebooks/{担当名}.md`）

担当者の引き継ぎノート。担当者が作業の最初に読む。

- 「改善アクション（実施中）」: `team_log.py sync-notebooks` が書く（手で直さない。正本は `team/actions.jsonl`）
- 「管理担当からのフィードバック」: 管理担当が毎月書き換える
- 「続けている教訓」: 管理担当が、繰り返し効いている教訓だけを残す（ルールとして確定したものは CLAUDE.md・手順書・`kl_prompts/` に移して、ここから消す）
- KLチーム 初見視聴者担当 エマ（`kl-first-viewer`） のノートには回の中身（台詞・資料・論点）を書かない（初見の立場が崩れるため）
- **80行以内**（毎回読ませるため。超えたら管理担当が削る）
- 担当者は作業中にノートを書き換えない。気づいたことは報告に書き、メインが `team_log.py add --note` か `feedback` で残す
