# 旧形式（kl001〜kl030、独白形式）の記録

> この文書は 2026-10-24 に CLAUDE.md から移した詳細・記録。本文は移す前のまま（見出しの名前も同じ。コードや手順書の「CLAUDE.md「〇〇」参照」は、ここの同名の節を指す）。

#### 旧形式（kl001〜kl030）のBGM方針の記録（2026-08-21〜2026-10-05）

以下は独白形式のときの方針。掛け合い形式（kl031以降）には上の方針を使う。

**BGMルール（SCとは異なる、kagaku-life独自のトーン）:**
- **必ず温かく・希望が持てる・押し付けがましくないトーン**に限定する
  （SCの「重厚なオーケストラ調」路線はこのチャンネルには合わない —
  番組の核が「科学が主人公の暮らしにもたらす小さな幸せ」であるため）
- クエリに `warm` / `gentle` / `hopeful` / `uplifting` / `heartfelt` /
  `cozy` のいずれかを含めることを推奨する
- 禁止: epic, battle, war, dark, aggressive, horror, dramatic tension
  （壮大・攻撃的・悲壮すぎる曲は番組のトーンと合わない）
- 役割とトーンの対応:

| 役割 | 対象シーン | トーン | クエリ例 |
|---|---|---|---|
| intro（序盤） | teaser〜context | 自己紹介・課題の紹介、好奇心・静かな導入 | `"curious piano"` |
| main（中盤） | citation〜data | 研究紹介への高まり | `"warm uplifting"` |
| outro（終盤） | impact〜closing | 温かい余韻・小さな幸せ | `"heartfelt strings"` |

**2026-08-22確定:** 当初「intro=teaser〜citation」「main=context〜data」と
していたが、`citation`が`context`より後に来る通常のシーン並び順
（企画書のストーリー構成`hook→context→citation→finding`）ではBGMの3区間が
連続していないと成立せず矛盾していた。「自己紹介＋課題の紹介（〜context）」と
「研究の紹介（citation〜）」で区切る方が物語上自然という判断により、
`context`をintro側、`citation`をmain側に変更して確定した。`kl_video_gen.py`の
境界計算はシーンtype個別のハードコードではなく、上記の役割マッピング
（`teaser`/`hook`/`context`=intro、`citation`/`finding`/`data`=main、
`impact`/`closing`=outro）に基づき「実際の並び順で最初にintro以外の役割に
なった地点」を境界1とする実装。

**構成スクリプト:**
- `kl_bgm_qa.py` — BGM候補の音声QA（Geminiの音声理解でボーカル・台詞混入を
  自動検出。SCの `sc_bgm_qa.py` と同じ仕組み）
- `kl_bgm_library.py` — BGMライブラリ（`bgm_library.json`）管理。新規BGMの
  登録・エピソードへの紐付け（役割別 `bgm_sources[role]`）
- `kl_inject_bgm_credit.py` — CC BY曲のクレジットを `youtube_description` に自動注入
- `kl_bgm_final_check.py` — 選定した3曲の実音声＋制作確認書をGeminiに渡し、
  トーン適合・3曲の流れ・音質を最終判定（SCの音楽監督プロンプトをkagaku-life
  向けに書き換え）
- Freesoundからのダウンロード自体は lamp-whisper由来の共有スクリプト
  `$HOME/lamp-whisper/freesound_download.py` をそのまま流用する
  （`--library $HOME/kagaku-life/bgm_library.json` を必ず指定し、
  kagaku-life独自のライブラリで重複を判定させる）

**実行例:**
```bash
mkdir -p "$HOME/Desktop/kagaku-life/BGM"
FREESOUND_API_KEY=$FREESOUND_API_KEY python3 "$HOME/lamp-whisper/freesound_download.py" \
  "<Q_intro>" "<Q_main>" "<Q_outro>" \
  "$HOME/Desktop/kagaku-life/BGM/" \
  --round 0 --start-slot 1 \
  --library "$HOME/kagaku-life/bgm_library.json"

# スロット→役割プレフィックスへのリネーム後
python3 kl_bgm_qa.py --dir "$HOME/Desktop/kagaku-life/BGM"
```

**動作確認（2026-08-21、kl001で実施）:** 上記の流れで実際に3曲
（intro/main/outro）をダウンロードし、`kl_bgm_qa.py` で全曲ボーカルなしを
確認した。1回のクエリで0件になるケースがあり（Freesoundの30〜300秒・
CC0/Attributionフィルタに合致する曲が少ない）、SCと同様に該当スロットだけ
`--start-slot` で別クエリに差し替える運用が必要だった。テスト用にダウン
ロードした音声ファイルはgitにコミットしない（Desktop側で確認用）。
最終選定・ライブラリ本登録（`kl_bgm_library.py --add`）は、実際に聴いて
ユーザーの承認を得てから行う。

**候補の絞り込み方法（2026-08-21確定、SCの現行方式を踏襲）:** SCも
2026-08-04以降は`/consult`を使わず、**Claude（オーケストレーター自身）が
テキスト情報（曲名・タグ・`kl_bgm_qa.py`の音の説明）だけで役割ごとに
複数候補から1曲に絞り込み、実音声での検証は`kl_bgm_final_check.py`に
任せる**方式に変更している（BGM選定はオープンな戦略相談ではなく
タグ・制約への照合作業のため、`/consult`ほどの重さは不要と判断された）。
kagaku-lifeも同じ方式を採用する。

**テキストだけの絞り込みでは不十分な例（2026-08-21、kl001で実際に発生）:**
役割ごとに複数候補（各役割2〜3曲）をFreesoundから集め、曲名・タグを見て
introに "Atonal Crystal Chime"（風鈴・グロッケンで静かな曲、と判断）を
選んだが、`kl_bgm_final_check.py`の実音声チェックで「無調でSF的・冷たい
印象、チャンネルの温かいトーンと乖離」と判定された。テキスト情報だけでは
実際の質感（無調＝atonalの響き等）を見誤ることがあるため、**実音声での
最終検証（`kl_bgm_final_check.py`）を省略しない。** 差し替え後の再検証で
「温かみのあるアコースティックピアノ／ギター」に変更し、intro/mainは
「適合」、outroは「良曲だがやや情緒的すぎる可能性、ダッキング音量を
2〜3dB下げるか差し替えを検討」という条件付き採用の判定を得た——
このように**「一部だけ差し替え」の部分的なフィードバックが出ることも
想定し、3曲まとめてではなく役割単位で差し替え・再検証できるようにしておく**。

**新規候補を実績曲より優先して積極的に採用する方針に転換（2026-09-15確定）。**
kl022制作時、`bgm_library.json`を集計したところ、特に`main`役割はライブラリに
3曲しか存在せず、うち1曲（kl002-BGM-main）が全22話中9話（約41%）で
使い回されている偏りが判明した（ユーザー指摘で発覚）。原因は2つ複合していた:
(1) Freesoundの「warm/uplifting」系クエリでは新規候補が0件になることが
珍しくない（既知の制約、上記「動作確認」参照）、(2) それに加えて、
テキストによる一次絞り込みの段階で、上記kl001の「Atonal Crystal Chime」の
失敗（テキストだけでは質感を見誤り、実音声チェックで不適合と判定された）を
過度に警戒し、**新規候補が見つかっても実音声検証にすら進めず、無条件に
実績のある曲を「安全策」として選び続ける**傾向があったこと。結果として
`main`役割は2026-08のkl005以降、新曲が一度も追加されないまま17話が
経過していた。今後は、Freesoundで新規候補が1曲でも見つかった場合、
テキスト情報だけで「質感が不安」という理由で足切りせず、必ず
`kl_bgm_final_check.py`の実音声検証まで進めてから採用可否を判断する
（実音声検証は本来この目的のための工程であり、それを経ずに実績曲へ
逃げるのは工程の意図に反する）。実績曲は「無難な下限」であって
「デフォルトの正解」ではない、という前提で毎回の選定に臨むこと。

**`finding` シーンで成果の数値に触れる場合の画像表現（2026-08確定）:** ナレーションで
具体的な成功率等の数値を紹介する場合、image_promptにも反映して良いが、**AI画像生成は
数字・文字を正確に描けないため、パーセント等の数字テキストを直接指定しない**
（他のシーンと同じ "no text" 方針の一環）。代わりに、棒の高さ・円の塗りつぶし度合いなど
「割合が視覚的にわかるが数字は読めない」比較グラフィックをシーンの一部（コーナー要素等）
として指定する（例: before/afterで棒の高さが変わる、円グラフの塗りが増える、等）。

**研究紹介での所属機関・研究者名の扱い（2026-08確定）:** 信頼感を高めるため、
`finding`/`citation` シーンでは可能な限り実際の所属機関名（大学・企業名）を
ナレーションに明記する。ただし**研究者個人の人名（特に外国人名）はナレーションに
含めない**——日本語TTSでの発音が不自然になりやすいため。人名は `references` の
`lead_researcher` フィールドに記録し、概要欄・制作確認書でのみ表示する。

**`citation`/`finding`/`data`シーンに主人公を登場させない（2026-09-07確定、
全エピソード共通ルール）。** 全エピソードに共通する構造として、①主人公が
課題を抱えている（`context`）→②世界のどこかでその課題を解決しうる研究が
行われている（`citation`/`finding`/`data`）→③その研究が実現した未来の
暮らし（`impact`）、という3段構成を取っている。②の研究紹介パートは
「主人公とは無関係に、独立して行われている研究」を客観的に紹介する
パートであり、**主人公はその研究室・実験室に行ったことがない**（②の
時点ではまだ研究の存在を知ってすらいない場合が多い）。したがって
`citation`/`finding`/`data`シーンのimage_promptに主人公を登場させては
ならず、研究の被験者・実験参加者を描く場合は**主人公とは明確に異なる
容姿の匿名の人物**（年齢・体型・髪型・髪色等を主人公と意図的に変える）
として描くこと。kl016で被験者の容姿を主人公と同一にしてしまい
（`graying short hair matching his appearance in other scenes`のような
記述を誤って被験者にも流用した）、ユーザーから「研究室にいる患者は
主人公とは別人のはず」と指摘を受けて修正した実例がある。STEP2の
image_prompt生成時、`citation`/`finding`/`data`シーンに描く人物が
`protagonist`と同一人物になっていないか機械的に確認すること。

### ストーリー構成と2ナレーターボイス制（2026-08確定、2026-10-04から旧形式の記録。新形式は冒頭「掛け合い形式への転換」）

企画書の「物語調」演出を徹底するため、単なる論文解説ではなく以下の構成で語る。

0. 冒頭の離脱回避ティザー（`teaser`、2026-08-21追加）
1. 主人公の簡単な自己紹介（`hook`）
2. 主人公が抱える課題の説明（`context`）
3. それを解決しうる研究の紹介（`citation` / `finding` / `data`）
4. それが実現したときの未来の暮らし（`impact`）
5. 締め（`closing`）

**`teaser`について（2026-08-21追加）:** samurai-chroniclesが冒頭に離脱回避
ティザーを設けているのに倣い、本編で一番「面白い部分」（`impact`シーンの
未来の暮らし）が動画の後半まで出てこない構成による序盤離脱を防ぐため追加。
`hook`（自己紹介）に戻って本編を始める前に、`impact`シーンの内容を数秒だけ
先出しする。ナレーターは主人公自身の未来を見せる形になるため生活者ボイス。
`image_prompt`は先出しする`impact`シーンと同じ内容を指定してよい
（`kl_video_gen.py`実装時に同一素材を使い回すか、別途生成するかは
そのとき判断する）。

**複数カットの高速フラッシュ構成にする（2026-08-21改訂）:** 当初は`teaser`を
1シーン（約8秒、単一の未来カット）としていたが、8秒を2秒×4カットに分割し、
複数の異なる`impact`シーン（朝・夕方・週末など）を矢継ぎ早に見せてから、
最後に短い問いかけで締める構成に変更した。1カットだけよりテンポが出て
「引き」が強くなる。2秒の尺に収めるため、各カットのナレーションは10〜15字
程度の短いフレーズに抑える（日本語ナレーションは概ね4〜5字/秒。目安は
`kl_confirmation_doc.py`の`estimate_seconds`と同じ250〜300字/分）。最後の
締めのカットだけは問いかけの完結のため少し長め（4秒程度）でもよい。

**ナレーターは2声を使い分ける。** 主人公パート（1・2・4）は主人公と同性の
「生活者ボイス」、研究解説パート（3）は主人公と異性の「研究ボイス」を使う
（例: 主人公が女性なら研究解説パートは男性ボイス）。物語部分と研究解説部分を
声で切り替えることで、聞き手にも構成の切り替わりが自然に伝わる。

**締め（`closing`）は研究ボイスに戻す（2026-08-20確定）。** `citation`（研究ボイス）で
開き、`closing`（研究ボイス）で締めることで、物語の内側（生活者パート）を客観的な
語りが挟み込む構成にする。生活者パートが一人称の独白調になるため、最後だけ視点が
戻らないと「誰が語っているか」が曖昧になりやすいという理由もある。

**生活者パートは一人称の語り口にする（2026-08-20確定）。** `hook`/`context`/`impact`
は「田中美咲さん、34歳。〜そんな日々を送っています」のような三人称の説明調ではなく、
「34歳。〜そんな毎日です」のように主人公自身が語っている一人称の独白として書く
（主語の「私」は必要な箇所以外は省略してよい、自然な日本語の一人称語りを優先する）。
`citation`/`finding`/`data`/`closing`（研究ボイス）は引き続き客観的な説明調で書く。

**`impact` の未来描写は「想像している」ことを毎回明言せず、その場にいる感情として
描く（2026-08-20確定）。** `impact` は「もし実現したら」という前提をシーン冒頭で
1回示せば十分で、以降のシーンで「〜かもしれません」「そんな想像が頭をよぎります」
といったヘッジ表現を繰り返す必要はない。むしろ未来ドラマの中に入り込んで、その状況を
心から喜んでいる・安堵している、という没入感のある感情表現を優先する（例:
「コーヒーを味わえる——そんな余裕が、うれしくてたまりません」）。ヘッジを重ねすぎると
説明的になり、主人公自身の生きた感情から遠ざかる。

**`impact`ブロックの最初の1シーンだけ「思考の吹き出し」で現実と区別し、
以降は雲なしで没入させる（2026-08-25確定、複数回の試行錯誤の末に決定）。**
ナレーションでヘッジしすぎない上記方針の一方、`impact`ブロック（本編中盤〜
終盤に連続する複数の`impact`シーン。ティザーでの先出しは対象外）が現実の
続きなのか主人公の想像なのか、絵だけでは判別しにくいという指摘がkl004で
あった。

- **最初の`impact`シーンのみ**: 主人公を小さく（現実の部屋・窓辺の椅子等に
  座った姿）描き、頭から古典的な漫画風の「思考の吹き出し」（頭から小さな
  丸が連なって大きな雲形の吹き出しにつながる、あの見慣れた記号）を出し、
  その吹き出しの中に、これから始まる想像の情景（次シーン以降と同じ内容の
  縮小版）を描く。これによって「ここから先は想像です」という合図を一度
  だけ明確に出す。
- **2枚目以降の`impact`シーン**: 雲や吹き出しの演出は一切つけず、他の
  シーンと同じ通常の物語調イラストとして、主人公の姿を画面いっぱいに
  没入感高く描く（1枚目で「想像に入った」ことが視聴者に伝わっているため、
  以降も雲の縁取りを引きずる必要はない、というのが最終判断）。
  **ただし絵だけでは想像シーンである合図が弱まるため、2枚目以降の
  `impact`シーンには`scene.badge_text: "幸せな未来を夢想中"`を必ず設定する
  （2026-08-27追加、`kl_video_gen.py`の`burn_telop_global`が実装。
  telop_cardsとは独立した仕組みで、シーンの表示時間を通して画面左上に
  常時ラベルとして焼き込まれる——発話タイミングに追従するテロップとは
  別物）。1枚目（吹き出し演出のあるシーン）には付けない。kl005 S15〜S16・
  kl006 S14〜S15で実装済み。kl007制作時にこの設定自体をSTEP2生成時に
  見落とす事故が発生したため、STEP2完了後の機械的チェック項目に追加する
  （`impact`シーンが複数ある場合、2枚目以降全てに`badge_text`があるか確認）。**

**没却した中間案（記録として残す）:** 全`impact`シーンに雲の縁取りを
毎回つける案、雲がフレームの四辺からはみ出す構図、複数シーンで背景
（部屋・窓・人物サイズ）を完全一致させる案（`--reference-scene`オプションで
参照画像を渡す方式は実装したが、最終的にこのエピソードでは不要と判断）を
順に試したが、最終的に「1枚目だけ吹き出し、以降は雲なし」がシンプルかつ
効果的と判断された。`--reference-scene`の仕組み自体（`kl_image_gen.py`）は
残してあり、**2026-09-29からは`/kl-new` STEP6.6/6.7のクロスシーンQAで、
主人公・家族・統合ロボットの同一性がずれたシーンを、同一性が正しい別シーンを
参照画像にして1シーンずつ再生成する用途に使う**（テキストのdescriptor追記だけ
では独立生成ごとの細部のばらつきが収まらないため。lamp-whisper LW088で同じ
方式が有効だった）。ただし用途は人物・ロボットの同一性に限り、構図・背景の
コピーには使わない（上記kl004の判断どおり、背景の完全一致は不採用）。
kl004 S13〜S16で実装・QA確認済み（[episodes/kl004.json](episodes/kl004.json)
の該当プロンプト参照）。

**全エピソード共通の「オチ」（2026-08-20確定）: 科学の本当の価値は、それが
主人公の暮らしにもたらす小さな幸せである、という着地点で終える。** 技術そのものの
すごさ（性能・数値・野心度）はSTAGE4で評価する選定基準ではあっても、エピソードの
感情的な締めくくりにしてはいけない。`impact`シーンで描く朝・夕方・休日のような
具体的な瞬間は、単なる機能紹介の羅列ではなく、主人公がそこで感じる小さな喜び・安堵・
愛おしさそのものが主題である。`closing`（研究ボイス）は技術の現在地（まだ研究段階等）
を正直に示しつつ、その先に主人公の暮らしがあるという着地に触れて締める。kl001
（朝のコーヒー・家族の食卓・娘との週末）がこの型の実例。

**`closing`の末尾2文は固定フレーズ（2026-08-25追加）:** 上記の情緒的な着地の
