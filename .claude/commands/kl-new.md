# /kl-new — くらしを変える科学 新エピソード制作

論文選定（STAGE1〜5）からエピソードJSON生成・動画完成までの全工程を実行するコマンド
（2026-08-24、`/kl-topic`を統合。旧`/kl-topic`は廃止し、このコマンド1つに一本化した）。
各ステップは人間の確認を挟みながら進める（SCの`sc-new.md`と同じ設計思想: 重い創作ステップは
サブエージェントに委任し、オーケストレーター＝この会話はスクリプト実行と検証・進行管理に
専念する）。

> 論文選定（STEP1のSTAGE1〜5）は2026-08時点では軽量版。STAGE5の判断基準（「動画にしやすさ」
> 等の実務観点での選び直し）はまだパターン化できていないため、都度の会話に委ねる。何周か
> 運用して判断パターンが固まってきたら、このコマンドに反映していく。

## STEP 1 — トピックを確定する

`topics_queue.json` の `queue` 配列に、先頭に `status: "confirmed"` のエントリがあるか確認する。

### ケースA — 既に確定済みトピックがある場合

そのエントリを次のエピソードとし、`episode_id`・`title`・`entry_question`（視聴者側の問い）・
`references`（複数可）・`protagonist`・`notes`（ストーリーコンセプト）をユーザーに要約提示し、
この内容で進めてよいか確認する。OKが得られたらSTEP2へ進む。

### ケースB — 確定済みトピックがない場合（関心ごとの選定から開始）

2026-09-29に「論文のプールを採点して上位から選ぶ」方式から「視聴者の関心ごとから入り、
その関心ごとに答える論文を探す」方式へ作り直した（経緯・根拠は `PIPELINE_REDESIGN.md`、
CLAUDE.md「論文選定ロジック」）。以下のSTAGE0〜5を順に実行し、`topics_queue.json` に
新規`confirmed`エントリを追記してからケースAの手順に進む。

#### STAGE 0 — 次に扱う関心ごとを決める

```bash
/usr/bin/python3 kl_concern_select.py
```

直近の回と `viewer_concerns.json` の選定ルールから、この回で使える枠（健康系・ワイルドカードの
残り）と、選べる関心ごとの上位3件（当事者の広さ・前回からの間隔の順）が出る。これをそのまま
ユーザーに提示し、どの関心ごとにするかを決めてもらう。

- 提案以外の選べる関心ごとも見たい場合は `--all` で全一覧を出す
- 健康系の枠が埋まっている回は、健康系の関心ごとは提案に出てこない（スクリプトが除外する）
- ワイルドカード枠が残っている回は、関心ごとの代わりに**ワイルドカード回**
  （関心ごとを持たず、意外性・感動で選ぶ回）にすることもできる。その場合は下の
  「ワイルドカード回の手順」へ進む
- 関心リストに無いが扱いたい関心ごとをユーザーが挙げた場合は、根拠（公的統計・検索候補など）を
  確認したうえで `viewer_concerns.json` に追加してから進める

#### STAGE 1 — 論文を集める（関心ごと単位）

`topics_shortlist.json` に、その関心ごと（`concern_id`）の `status: "available"` が
**3件以上**あれば、検索は省略してSTAGE2へ進む。その前に必ず採点バージョンのゲートを通す:

```bash
/usr/bin/python3 kl_shortlist_rescore.py --check
```

非ゼロ終了なら `kl_shortlist_rescore.py --concern {id}` で再採点してから提示する。
`--check` が「既視感判定が最新エピソードを見ていない」と警告した場合は、直近の回と同じ型の候補が
既視感なしのスコアのまま残っている前提で読み、必要なら `--stale-deja-vu` で再判定する。

3件未満なら、次を順に実行する（Semantic Scholarの検索とGemini呼び出しを伴う）:

```bash
/usr/bin/python3 kl_paper_search.py --concern {id}
/usr/bin/python3 kl_paper_triage.py --concern {id}
/usr/bin/python3 kl_paper_screen.py --concern {id}
/usr/bin/python3 kl_venue_allowlist_update.py
/usr/bin/python3 kl_paper_hypecheck.py --concern {id}
/usr/bin/python3 kl_paper_interest_score.py --concern {id} --top 10
/usr/bin/python3 kl_shortlist_add.py
```

- `kl_paper_triage.py`（STAGE1.5）は、検索で集まった数百〜数千件をタイトルとアブストラクト冒頭だけで
  まとめて判定し、「その関心ごとを持つ一般の人への答えになりそうか」の上位40件だけをSTAGE2へ送る。
  関心ごと起点の検索は旧カテゴリよりヒット件数が桁違いに多く（実測: 睡眠で2,664件）、STAGE3・4を
  全件に回すと時間もコストも見合わないため。被引用数は使わない
- `kl_venue_allowlist_update.py` は提案のみ行う。提案された掲載誌をユーザーに見せ、追加してよいか
  確認してから `--apply` で反映する（低品質誌を誤って許可リストに載せないため）

関心ごとごとに簡潔な件数サマリのみ報告する（生データは画面に出さない）:

```
[{関心ごと}]
STAGE1: 収集{N}件 → プレフィルタ通過{N}件（うちプレプリント{N}件）
STAGE1.5: 上位{N}件をSTAGE2へ（最低点{N}）
STAGE2: pass={N}（うち許可リスト自動pass{N}） flag={N} exclude={N}
STAGE3: ok={N} caution={N} high_risk={N}
STAGE4: 上位{N}件をランキング
```

#### STAGE 2 — 候補を提示する

`topics_shortlist.json` のその関心ごとの `available` 候補を、総合スコア順に上位5〜10件提示する。
各候補について次を見せる:

- **視聴者側の問い**（`entry_question`）と総合スコア
- スコア内訳。特に `wonder_score`（最重要）・`answer_fit_score`（その悩みに本当に答えているか）・
  `applicable_breadth_score`（当てはまる人の広さ）は単独の数値として見せる
- `evidence_level`（ヒトの試験か、動物実験だけか等）。動物実験・細胞だけの研究は答えの適合度が
  コード側で2点以下に抑えられている
- `market_status`・`novel_delta`（市場に既にある部分と本当に新しい部分）、`future_scene_sketch`
- `behavioral_familiarity: familiar` と `deja_vu_level: strong` のラベル（どちらもwonder/transformationが
  コード側で上限3にキャップされている。ラベルを見せずにスコア順に並べない）。`deja_vu_note` が
  空でない候補は指摘内容を明記する（除外はせず判断材料として見せる）

同じ技術の型の候補が3件以上上位に来ている場合は、その型からは上位2件までを提示し
「他に◯件、同種の候補あり」と注記する。

#### STAGE 2.5 — ストーリー案を2〜3案提案する

上位候補から、実際にどの論文（複数可）でどんな回にするかを2〜3案提案する。各案に含めるもの:

- **視聴者側の問い**（タイトルとShortsのフックの土台になる。論文が示した範囲を超えて一般化しない）
- **使用する論文**（複数本なら組み合わせる必然性）
- **主人公の設定**（その関心ごとを抱える生活者。職業・年齢・抱える悩み）
- **一言ストーリーコンセプト**（悩み→研究→未来の暮らし）
- **なぜ面白いか**（wonder・答えの適合度・当てはまる人の広さとの対応）

#### STAGE 3 — 既知のパイプラインギャップを踏まえて補足する

CLAUDE.md STAGE2に記載の通り、Semantic Scholarがプレプリント版と正式出版版を別レコードとして
統合していない場合、優れた論文がSTAGE1の自動探索から漏れることがある（kl002の実例）。
ユーザーが「他にこういうテーマはないか」と聞いてきた場合や、上位候補の質に納得できない場合は、
WebSearchで補助的に探してよい。査読済み掲載であることを出版元の公式ページURLで人間が直接確認
できれば、`pipeline_gap_flag: true` を付けて候補に加えられる。

#### STAGE 4 — 人の最終ゴーサイン

提案したストーリー案（または修正案）のどれで行くかをユーザーに確認する。「動画にしやすさ」
（統計的ヘッジの複雑さ、絵作りのしやすさ、主人公の物語の組み立てやすさ）も踏まえて一緒に検討してよい。
あわせて、直近5話程度の**実際の内容の型**（研究の型・アプローチ）が連続していないかも確認する
（CLAUDE.md STAGE5「カテゴリのローテーションだけでは内容の型の偏りを検出できない」）。

#### STAGE 5 — topics_queue.jsonに追記する

確定した回を `topics_queue.json` の `queue` 配列末尾に追記する。

- `episode_id`: 既存の最大値+1（`kl{NNN}`）、`status`: `"confirmed"`
- `slot_type`: `"concern"`（関心ごと起点）／`"wildcard"`（ワイルドカード回）
- `concern_id`: 関心ごとのid（ワイルドカード回は近いものがあれば記入、無ければ `null`）
- `domain`: 関心ごとの領域（`body`/`disease`/`daily`/`life`）。ワイルドカード回も内容に近い領域を
  1つ入れる（健康系の上限の判定と公式サイトの分類に使う）
- `entry_question`: 視聴者側の問い
- `title` / `format` / `references[]`（`title`/`authors`/`year`/`venue`/`url`または`doi`/`is_preprint`） /
  `protagonist` / `hook_idea` / `notes`
- `stage4_snapshot`: 採用した論文の選定時点のSTAGE4スコア（在庫の該当エントリから
  `overall_score`・`score_breakdown`・`evidence_level`・`market_status`・`novel_delta`をコピー）。
  事前の採点と実際の視聴データが合っていたかを後で `/kl-analytics` で検証するため
- `pipeline_gap_flag: true` の候補を採用した場合はその旨と根拠を `notes` に明記する

採用した論文の在庫エントリ（`paperId` で照合）を `status: "used"`・`used_in: "kl{NNN}"` に更新する
（ワイルドカード回で旧在庫から採用した場合は `topics_shortlist_legacy.json` 側を更新する）。

**単に今回選ばれなかった候補（`available` のまま、削除しない）と、ユーザーが明示的に
「既視感がある」「面白みに欠ける」等の理由で却下した候補（`status: "rejected"`・
`rejected_reason` に理由）を区別する。** 却下を記録しないと、次回以降も同じ候補が提示され、
既視感の判定（`kl_paper_interest_score.py` の `build_past_episodes_context()` が却下済みを
参照する）も機能しない。ユーザーが候補を明示的に否定した発言は、その場でこのステータス更新に
反映すること（STAGE5の追記時だけでなく、STAGE2〜4の途中でも）。

追記後 `total_topics` と `last_updated` を更新する。コミットメッセージには選定理由を残す。
追記後、ケースAの手順（要約提示・確認）に進み、OKが得られたらSTEP2へ進む。

### ワイルドカード回の手順

STAGE0でワイルドカード回を選んだ場合（ワイルドカード枠が残っている回だけ）:

1. 候補は、制作者の直感で持ち込まれた研究（kl021のような例）か、旧在庫
   `topics_shortlist_legacy.json` の `status: "available"` の上位（`overall_score` 順）から選ぶ。
   旧在庫のスコアは旧方式の採点なので、`deja_vu_note`・`market_status` と合わせて参考程度に見せる
2. 使う候補が決まったら、旧在庫の候補は最新の採点で採点し直す:
   `/usr/bin/python3 kl_shortlist_rescore.py --legacy-paper-id {paperId}`
   （関心ごとを持たないワイルドカードの採点。life_relevanceを含む従来の重みで採点される）
3. STAGE2.5（ストーリー案）→ STAGE4 → STAGE5 に合流する。`slot_type: "wildcard"`

## STEP 2 — エピソードJSONを生成する（サブエージェントに委任）

このSTEPの生成（`episodes/kl{NNN}.json` 全体の作成）は `Agent` ツールで
**model指定なし（Sonnet相当）**のサブエージェントに委任する
（`run_in_background: false`、結果を待ってからSTEP3へ進む）。

サブエージェントは会話履歴を持たないため、Agentプロンプトには以下を
すべて明示的に含めること:

- STEP1で確定した `entry_question`（視聴者側の問い。タイトル・ティザー1カット目・`hook_lines`・
  Shorts1カット目の土台） / `references` / `protagonist` / `notes`（ストーリーコンセプト）
- 下記「生成ルール」節の全文
- 出力先パス `$HOME/kagaku-life/episodes/kl{NNN}.json` に直接JSONファイルを
  書き込むよう指示する（オーケストレーター側では保存しない。画面にJSON全体を
  出力させない）

完了後、オーケストレーターは保存されたJSONのシーン数・スキーマ妥当性に加え、
**`scenes`配列の`type`順が下記「生成ルール」節の固定順序
（`teaser* → hook → context → citation → finding → data → impact →
closing`）と一致しているかを機械的に検証する**（2026-08-26追加。
サブエージェントへのプロンプト指示だけでは順序ミスが実際に発生したため、
STEP2直後にオーケストレーター側でも必ず確認する）。ズレていればSTEP2の
Agentに差し戻すか、オーケストレーター自身がscene_idを振り直して修正する。
**あわせて、`impact`タイプが2シーン以上ある場合、2枚目以降全てに
`scene.badge_text: "幸せな未来を夢想中"`が設定されているかも同じタイミングで
機械的に確認する（2026-08-29追加。kl007でこの設定を丸ごと見落とし、
動画完成後にユーザー指摘で発覚する事故が発生した。1枚目には付けない）。**
**さらに、`hook`シーンの`narration`が`protagonist.name`（の氏名部分）を
文字列として含んでいるかも同じタイミングで機械的に確認する（2026-09-01
追加。kl001〜kl011の`hook`は「高橋健太、42歳。建築設計士です。」のように
必ず氏名を名乗って始まる型だったが、kl012でこの型が崩れ「34歳、Web広告
代理店で〜」と氏名抜きで始まってしまい、STEP5のOpusレビューでも
拾われずSTEP11の人間確認で発覚した。指示語の有無を問わずシーン単体で
完結しているかを見るOpusの観点5とは別に、こちらは単純な文字列包含
チェックで機械的に検出できるため、Opus任せにせずここで確認する）。**
**トップレベルの`hook_lines`（2要素配列）が設定されているかも同じタイミングで
機械的に確認する（2026-09-06追加。CLAUDE.mdに記載が無かった期間にkl006・kl013・
kl014の3話で`hook_lines`が丸ごと欠落する事故が起きたため）。**
**2026-09-29追加（見せ方の変更、`PIPELINE_REDESIGN.md` フェーズ2）: 次も同じタイミングで
機械的に確認する。① `youtube_title` に「【幸せな未来のサイエンス】」等のチャンネル名が
入っていない、② `shorts[0].scenes[0].narration` が15字以内（1〜2秒で言い切れる長さ）、
③ `shorts[0].scenes` の最後のカットのナレーションに「本編」が含まれている、
④ `shorts[].face_hook_image_prompt` が無い（廃止した無音の顔アップカットを作らない）。**
**最後に、`citation`/`finding`/`data`シーンのimage_promptが`protagonist`と
同一人物を描いていないかも同じタイミングで確認する（2026-09-07追加。これらの
シーンは主人公とは無関係に行われている研究の客観的な紹介パートであり、主人公が
その研究室に行ったことはない。研究の被験者・実験参加者は主人公とは明確に
異なる容姿の匿名の人物として描く必要がある。kl016で被験者の髪型・髪色の
記述が主人公と同一になってしまい、ユーザー指摘で修正した事故があった。
image_prompt中に`protagonist`の名前や「主人公と同じ髪型/髪色」のような
主人公限定の描写がcitation/finding/dataシーンに紛れ込んでいないか、
文字列レベルで確認するとよい）。**
内容の細部レビューはSTEP5の制作確認書で行う。

### 生成ルール

**動画尺・シーン数:** 目標7〜9分、10〜15シーンの可変レンジ（複数論文回は
15シーン程度まで許容）。クリップ尺は実際のナレーション音声長から決まるため、
`duration_seconds` はフォールバック専用（目安値でよい）。

**シーンタイプとBGM役割:**

| type | 内容 | BGM役割 | 画風 | ナレーター |
|---|---|---|---|---|
| `teaser` | 冒頭の離脱回避ティザー（`impact`の一部を数秒先出し） | intro | 物語調 | persona |
| `hook` | 主人公の自己紹介（3〜5秒） | intro | 物語調 | persona |
| `citation` | 出典明示（大学名・発表年等、人名は含めない） | intro | 物語調 | research |
| `context` | 主人公が抱える課題の説明 | main | 物語調 | persona |
| `finding` | 研究の紹介（内容・手法・結果） | main | 物語調 | research |
| `data` | グラフ・比較図 | main | チャート調 | research |
| `impact` | 実現した未来の暮らし（主人公視点） | outro | 物語調 | persona |
| `closing` | 締め | outro | 物語調 | research |

境界計算: 境界1(intro→main)=最初の`context`/`finding`開始、
境界2(main→outro)=最初の`impact`開始。

**`scenes`配列の並び順は固定・厳守（2026-08-26追加）:** 上記の表の順に、
必ず `teaser* → hook → context(1〜2) → citation → finding(2〜3) →
data(0〜2) → impact(2〜4) → closing` の順で並べること。**`citation`
（出典明示）を`context`（課題の説明）より前に置かない。** BGM境界計算
（上記）はシーンの実際の並び順に基づいて機械的に算出されるため、
順序を間違えると「境界1=最初のcontext/finding開始」の判定がズレて
BGMの切り替わりタイミングも壊れる。物語の流れとしても、課題（`context`）を
先に示してから出典（`citation`）で解決策の存在を示す方が自然（kl001〜004の
実績と同じ順）。kl005で実際にcitationがcontextより先に生成されるミスが
発生し、STEP5の人間確認で発覚してSTEP2に差し戻した。

**`teaser`（4シーン・各2秒前後）:** `impact`シーンの内容を先出しする複数カットの
高速フラッシュ構成（1カットのみにしない）。各カットのナレーションは10〜15字程度の
短いフレーズ。最後のカットだけ問いかけで締める、やや長め（3〜4秒）でもよい。
**2026-09-29改訂（本編の冒頭10秒で「何の話か」を約束する。YouTube公式の助言
「長尺動画は冒頭5〜10秒で約束した話題に入る」に対応）: 1カット目のナレーションは
`entry_question`（視聴者側の問い）を主人公の言葉で言う。2カット目以降で答えのさわり
（未来の暮らしの場面）を見せ、最後のカットで問いかけて締める。本編冒頭のロゴイントロ
（4秒）は廃止したので、ティザーの直後がそのまま`hook`（主人公の自己紹介）になる。**
ナレーターはpersona。**あるteaserカットが本編（多くはimpact）の特定シーンと
同じ場面（同じ人物・同じ構図）を先出しする場合は、`image_prompt`を新規に書かず、
対応する本編`scene_id`を`"reuse_scene_id"`として指定する**（`kl_image_gen.py`が
その画像をコピーして使い回すため、ゼロから独立生成しない — コスト削減、
フラッシュフォワード的な演出としても自然。2026-09-04導入）。本編に対応する
場面が無いカット（オリジナルの導入カット等）のみ、従来通り`image_prompt`を
新規に書く（`reuse_scene_id`は付与しない）。

**2ナレーターボイス制・語り口:**
- persona（生活者パート: `teaser`/`hook`/`context`/`impact`）は**一人称の独白調**
  （三人称の説明調にしない）。主語の「私」は必要な箇所以外省略。
- research（`citation`/`finding`/`data`/`closing`）は客観的な説明調。
- `impact`は「もし実現したら」を1シーン目（最初のimpactシーン）で示せば十分。
  以降のシーンでヘッジ表現（〜かもしれません、想像しています等）を連呼せず、
  没入感のある感情表現を優先する。
- `closing`は必ずresearchボイスで締める（citationと対になる客観的な語り）。
- **全エピソード共通のオチ:** 科学の本当の価値は主人公の暮らしにもたらす
  小さな幸せである、という着地で終える。技術のすごさ自体を感情的な締めに
  しない。`impact`は朝・夕方・休日等の複数の具体的瞬間に分けて描く。
- **`closing`の末尾2文は固定（2026-08-25追加）:** 情緒的な着地の直後に、
  (1)「詳しい研究内容が知りたい方は概要欄をご確認ください」の趣旨の一文
  （こちらは要旨が保たれていれば多少の言い換え可）、(2)チャンネル登録を
  促す一文、を必ず加える。**(2)は2026-08-31時点で完全な固定文言に確定した。
  エピソードの題材に合わせて言い換えない（言い換えていた結果、kl009で
  「誰かの『自分の脚』を取り戻すのでしょうか」のように義足エピソード限定の
  表現になってしまい、ユーザーから毎回変えず固定にするよう指示された）。
  対外的なチャンネル名「幸せな未来のサイエンス」を彷彿させる文言にとの
  追加指示も踏まえ、以下に確定。毎回そのまま一字一句このまま使う:**

  「次はどんな研究が、誰かの幸せな未来を運んでくるのでしょうか。その瞬間を
  これからも一緒に見つけていきたい方は、ぜひチャンネル登録してお待ちください。」

**研究紹介の書き方:**
- 実際の所属機関名（大学・企業名）は明記する。研究者個人の人名（特に外国人名）
  はナレーションに含めない（日本語TTSでの発音が不自然になりやすいため）。
  人名は `references[].lead_researcher` に記録するのみ。
- 成功率等の具体的な数値をできるだけ盛り込む（研究の説得力になる）。
- 「査読」「プレプリント」の語はナレーションで使わない（概要欄で開示）。
  代わりに「まだ研究段階のプロトタイプ」等の一般的な表現でヘッジする。
- **健康の話題は「研究結果の紹介」にとどめる（2026-09-29追加）。** 視聴者への健康上の
  助言・指示（「〜しましょう」「〜を試してみてください」「〜すれば治ります」、薬・サプリ・
  治療法を勧める、用量を示す）を書かない。語り手（研究ボイス）に医師・専門家・研究者本人を
  名乗らせない。研究段階の結果（動物実験・小規模試験・承認前の治療）を、確立した治療法や
  誰にでも効く方法のように語らない。主人公の独白（自分の体験・気持ち）は助言に当たらない。
  理由: YouTubeは2026年7月、AIの語り手が専門家を装って健康の助言をする内容を収益化の
  対象外にした。研究結果の紹介・議論自体は医療誤情報ポリシーの例外として明記されている。
  `kl_fact_check.py` がこの3点をエピソード全体でチェックする（STEP4）。

**画像プロンプト（`image_prompt`）:**
- **シーン内容のみを書く。スタイルキーワード（palette/lighting/no anime等）は
  書かない**（`kl_image_gen.py`がシーンtypeに応じてBASE_CONTEXT/CHART_CONTEXTを
  自動付与するため、二重指定・スタイル相反を避ける）。
- 登場人物の性別・年齢を明記する（特に子供。性別未指定だと誤った性別で
  生成されるバグが実際に起きた）。
- 時間帯は視覚的に明示する（例: "soft morning daylight, not night"、
  "evening, dusk sky visible through window"）。時間帯を言葉だけで示すと
  夜空を誤生成することがある。
- `finding`シーンは研究室での実験風景にする（家庭内シーンにしない）。
  研究者は**分野を問わず白衣を着せる**（経済学・社会科学系の研究でも、視認性・
  「この人は研究者」という一目での伝わりやすさを優先する。kl002で経済学研究
  という理由で白衣を外した結果ユーザーから指摘があり、分野に関わらず白衣を
  着せる方針に統一した、2026-08-23）。論文の実施国に応じた人種で描写する
  （世界各地で独立した研究が進んでいることを視覚的に示す）。データはコーナーの
  小さなフラットグラフィック（全体の1/8以下、no text/numerals）でさりげなく
  示してよい。
- **`citation`/`finding`/`data`シーンに主人公を登場させない（2026-09-07追加、
  全エピソード共通ルール）。** これらのシーンは「主人公とは無関係に、世界の
  どこかで独立して行われている研究」を客観的に紹介するパートであり、主人公は
  その研究室・実験室に行ったことがない（多くの場合、②の時点ではまだ研究の
  存在を知ってすらいない）。したがって`citation`/`finding`/`data`の
  image_promptに主人公を登場させてはならず、研究の被験者・実験参加者を描く
  場合は**主人公とは明確に異なる容姿の匿名の人物**（年齢・体型・髪型・髪色等を
  意図的に変える）として描くこと。「主人公と同じグレーヘア」のような、他の
  シーンの主人公描写をそのまま流用した記述をうっかり被験者にも使い回さない
  よう注意する（kl016で実際に発生し、ユーザー指摘で修正した事故）。
- `data`タイプは物語シーンと別トーン（`kl_image_gen.py`が自動適用）。
  内容は棒グラフとは限らない（壁+矢印+トレンド線等、内容に応じて自由に
  構図を指定してよい）。
- 未来パートの統合ロボットは全シーンで同一デザインを保つこと（説明文を
  使い回す）。ヒューマノイド的な人体プロポーション（頭・首・胴・腕・脚が
  人間らしい比率）を明記し、トイっぽい/マスコット的な見た目にならないよう
  指定する。フレンドリーだが機械的な顔（人間の顔に見えない）にする。
- 抽象的なアイコン（意味の伝わらない手のアイコン等）は避け、人物の様子・
  構図で伝える。
- 文字は一切入れない（"no text"を必ず含める）。
- 職業・学歴等の属性による比較を扱う回では、当該属性を必要以上に貶める
  表現にならないよう注意する（例: 「〜卒だから」という表現を、客観的な事実
  としてではなく本人の劣等感・コンプレックスとして描く。kl002で実際に
  指摘・修正した、2026-08-23。STEP5の配慮チェックとも対応）。
- **高齢の主人公を「高齢者らしく」見せるために、ストーリー上不要な杖・
  歩行器等の介助器具を画像生成AIが勝手に描き足すことがある（2026-08-25、
  kl004のShorts S01で実際に発生）。** ナレーションで「介護が必要な体では
  ない」等、主人公が介助器具を必要としないと明示している場合は、
  image_promptに"no cane, no walking stick, no walker, no mobility aid"
  のように明示的に禁止しておく（"no text"と同様、書かないと高確率で
  ステレオタイプ的に描き足されるため、省略ではなく明示的な否定が必要）。
- **`impact`ブロック（本編中盤〜終盤に連続する`impact`シーン群。ティザーでの
  先出しは対象外）は最初の1シーンだけ「思考の吹き出し」演出で現実と区別し、
  以降は雲なしで没入させる（2026-08-25確定）。** ナレーション側は想像で
  あることを繰り返しヘッジしない方針（本ファイル上記「2ナレーターボイス制・
  語り口」参照）だが、絵だけでは現実か想像か伝わりにくいという指摘があった。
  - **最初の`impact`シーンのみ**: image_promptで主人公を小さく（部屋の椅子等
    に座った現実の姿）描き、頭から古典的な漫画風の思考の吹き出し（頭から
    小さな丸が連なり大きな雲形の吹き出しにつながる）を出し、その吹き出しの
    中にこれから始まる想像の情景（次シーン以降と同じ内容の縮小版）を描く。
  - **2枚目以降の`impact`シーン**: 雲・吹き出しの演出は一切つけず、通常の
    物語調イラストとして主人公を画面いっぱいに没入感高く描く（1枚目で
    合図済みのため、以降雲を引きずる必要はない）。**あわせて
    `scene.badge_text: "幸せな未来を夢想中"`を必ず設定する（2026-08-27追加、
    1枚目には付けない）。`kl_video_gen.py`がシーン表示時間を通して画面左上に
    常時ラベルとして焼き込む（telop_cardsとは別物・発話タイミングに追従しない）。
    STEP2完了後の機械的チェック項目に追加すること（kl007でこの設定を
    丸ごと見落とす事故が発生した）。**
  - 全`impact`シーンに毎回雲をつける案・複数シーンで背景を完全一致させる案
    （`kl_image_gen.py --reference-scene`で参照画像を渡す仕組み自体は実装
    済み、他の演出で背景固定が必要な場合に利用可）も試したが、上記の
    「1枚目だけ吹き出し」が最終的に採用された。kl004 S13〜S16が実例。

**`references`/`reference_index`:** `finding`/`dataシーンには`reference_index`
（`references`配列のインデックス、0始まり）を付与する。単一論文回は0固定。

**タイトル（`youtube_title`、2026-09-29追加）:** `topics_queue.json` の `entry_question`
（視聴者側の問い）を土台にする。**主語は視聴者の問い・得・意外性にし、論文・大学・発表年を
主語にしない**（競合調査で、論文を主語にしたチャンネルは伸び悩み、伸びたチャンネルは
視聴者の悩み・疑問を主語にして論文を裏付けに回していた。`PIPELINE_REDESIGN.md` §1）。
- 型の例:「なぜ〜のか？」（素朴な疑問）／「〜は本当だった」「〜は間違いだった」（常識の反転）／
  「〜できる日が来る」（実現しつつある未来）
- 30〜40字を目安にする（スマホでは後半が切れる）
- 「【幸せな未来のサイエンス】」などチャンネル名を付けない（画面に常に表示されるので文字数の無駄）
- 大学・発表年・掲載誌は概要欄に書く。どうしても入れるなら末尾に短く（例「（Nature）」）
- `entry_question` と同じく、論文が示した範囲を超えて言い切らない（「〜が治る」ではなく
  「〜が治る日は来る？」等）

**thumbnail_prompt:** 16:9、統合ロボットの説明を含める（本編と同一デザイン）。
`thumbnail_headline`/`thumbnail_subcopy`も忘れずに設定する（未設定だとテキスト
合成がスキップされ、文字なしサムネイルになる事故が実際に起きた。STEP6参照）。
**2026-09-29追加:** 主要な人物・見せ場は画面の右半分に寄せ、左側に文字を置く余白を残す
構図にする（B案は左側に大きな文字を置くため）。

**`thumbnail_b`（サムネイルB案、2026-09-29追加。2026-10-01から任意・テスト一時中止中。
書かなくてよく、機械チェックの必須項目でもない。書けば `thumbnail_b.png` は作られるが、
アップロード後の「テストと比較」は依頼しない。`/kl-upload` STEP3参照）:** `{"keyword": "...", "line": "..."}`。
競合調査で伸びていた型（濃い地に極太文字、キーワード1語を最大）で、`kl_image_gen.py` が
A案と同じ背景から `thumbnail_b.png` を作る。`keyword` は一番目を引く1語（2〜6字、黄色で最大に
表示）、`line` は補足の1行（8〜12字、白）。合計10〜15字程度。アップロード後、YouTube Studioの
「テストと比較」でA案（`thumbnail.png`）と比べる（`/kl-upload`）。

**shorts（1本、5〜6シーン）:** 各カット2〜3秒の短いフレーズに区切る。
**構成は「1つの驚き・問い → 理由（研究を1〜2カット）→ 答えのさわり → 本編への誘導」
（2026-09-29改訂。旧構成は本編の要約＝主人公の悩み→研究→未来だった）。**
- **1カット目は、問いか一番の驚きを声で言い切る（15字以内、1〜2秒）。** 主人公の
  自己紹介や悩みから入らない。YouTube公式ブログ「Shortsのフックに使えるのは1秒」、
  Shortsはまず小さな層に見せて「視聴 vs スワイプ」の反応で配信が広がるかが決まるため。
  `hook_lines` はこの1カット目に重ねて表示される。1カット目の画は、感情の伝わる主人公の
  顔の寄りにしてよい（廃止した無音の顔アップカットの狙いはこの画で担う）
- **最後のカットは本編への誘導にする。** ナレーションで「答えは本編で」のように本編に
  触れる（「本編」の語を必ず含める）。`kl_video_gen.py` が最後のカットに「↓ 続きは本編で」を
  自動で重ねる。アップロード後、YouTube Studioで本編を「関連動画」に設定する（`/kl-upload`）
- 答えを言い切らない（続きを本編で見る理由を残す）**各カットが本編`scenes[]`の
既存シーンと同じ場面（同じ人物・同じ構図の再演）を描く場合は、
`image_prompt`を新規に書かず、必ず対応する本編`scene_id`を`"scene_id"`
として指定する**（`kl_image_gen.py`が本編で承認済みの画像を9:16に再構成
するため、ゼロから独立生成しない — コスト削減・一貫性向上、
samurai-chroniclesの同じ仕組みを踏襲、2026-09-04導入）。Shorts向けの
独自構図をわざわざ作る必要はない — フック・ダイジェスト・CTAいずれも
本編中の最も近いシーンを流用する。本編に対応する場面が無いカット
（独自のフック演出等）に限り、従来通り`image_prompt`を新規に書く
（この場合`scene_id`は付与しない）。チャート系のカット（`type: "data"`の
本編シーンを参照する場合、または独自カットで`"style": "chart"`を付与した
場合）は自動的にチャートスタイルが適用される。narrator/narration_voicesは
本編と共通。

**`hook_lines`（トップレベル、2行、必須）:** Shorts冒頭に大きく焼き込まれる
煽りテキスト（samurai-chroniclesの`shorts_hook_lines`踏襲）。日本語1行あたり
目安10〜16字程度、短く強いフレーズ2つで「これは何の話か」への好奇心を煽る
（例: kl001「洗濯物を／ロボットが畳む?」）。2026-09-29〜: 1行目は `entry_question`
（視聴者側の問い）か一番の驚き、2行目は答えのヒントにする。**2026-09-06追加。これまで
CLAUDE.mdに記載が無かったため、kl006・kl013・kl014の3話で設定漏れが発生した
実績があり、STEP2完了後の機械的チェック項目に追加すること。**

**`shorts[].face_hook_image_prompt` は2026-09-29に廃止した。** 冒頭2秒の無音の顔アップカットを
作らず、Shortsの1カット目から声を入れる（上記shorts節、CLAUDE.md「冒頭2秒の無音はやめる」）。

**チェック観点:**
1. **特定の属性への配慮**（学歴・職業・年齢・家族構成等）: 比較対象となる属性を

2. **生活実感との整合性**: 主人公の設定・状況描写に論理矛盾がないか（例:
   kl001で実際に発覚した「まだ存在しない製品への不安」のような、ストーリー
   自体の一貫性を壊す記述）。「もし実現したら」を待つ未来ではなく「今すぐ
   始められる一歩」として描くべき技術（既に実用化されている生成AI等）を、
   不必要に遠い未来のことのように書いていないか（kl002で実際に指摘された
   論点）。
3. **一人称/客観の語り口の一貫性**: persona/researchボイスの語り口ルール

4. **その他の台本品質**: 不自然な日本語、唐突な感情の飛躍、冗長な繰り返し等。
5. **シーン間の接続**（2026-08-31追加、2026-09-01に対象を拡張）: 各シーンを

   されていない前提・状況設定が、既に視聴者が知っている前提であるかのように
   唐突に持ち出されていないか、の両方を確認する。
   - (a)の典型例: citationシーンの書き出し（例:「この研究を進めているのは」）
     が、直前のcontextシーンではまだ研究そのものに触れていないのに唐突に
     「この研究」と始めてしまうケース（kl009で実際に発生）。
   - (b)の典型例: findingシーンで「パートナーがAIだと気づいた人ほど、任せる
     傾向が強まった」のように、参加者が「気づく」余地がある（＝相手が人間か
     AIかは実験中は知らされていない）という実験設計上の前提が、それより前の
     どのシーンでも一度も説明されていないまま持ち出されるケース（kl012で
     実際に発生、ユーザー指摘で発覚。STEP5のレビューはこの回でも実行済み
     だったが、指示語を伴わないこの種の「不在の前提」は見逃していた）。
   どちらも文法的には誤りがなく単体で読むと不自然に見えないため、観点1〜4の
   チェックだけでは見落とされやすい。「このシーンだけを読んだ視聴者が、
   前のシーンの情報なしに意味を理解できるか」を1シーンずつ自問しながら
   通し読みすること。
6. **制作確認書のチェックリスト項目（形式面）**: BGM未選択・サムネイル未生成は
   この段階では正常（STEP10・STEP6でそれぞれ生成するため）。ファクトチェックが

**なぜここだけOpusを使うか:** STAGE2/3や`kl_fact_check.py`が「Opusを使わない」
方針なのは、それらが検索グラウンディングで裏取りできる照合タスク（論文の数値と

ションの文章のみを対象にした人間視点レビュー（Opus）であるのと同じ考え方で、

3. **色・高さ・大きさの視覚的対応が、ナレーションが示す大小関係と矛盾して

## STEP 6.6 — 自動QAのall_okを鵜呑みにしない（2026-09-10追加・SC横展開）

STEP6の自動画像QA（`kl_image_gen.py`内、`QA_MODEL = "gemini-flash-latest"`）は、
samurai-chroniclesの同型パイプライン（`sc_image_gen.py`、全く同じモデル・同じ
`_correction_note`方式のリトライ機構）で、**偽陰性（誤った画像を"OK"と判定）と
偽陽性（正しい画像を誤って"NG"と判定）の両方が実際に発生した実績がある**
（ep098竹中半兵衛で確認）。KLはコードを移植した同一のQA機構を使っているため、
同じ限界を抱えている可能性が高い。

STEP6.5は`data`/`chart`シーンの「可読性」という別の観点のチェックであり、
**それ以外のnarrative系シーンについては、STEP6完了後この時点までClaudeが
一度も実際の画像を見ていない**（`all_ok: true`という文字列を信じているだけ）。
STEP11でユーザーに確認ページを見せる前に、主要シーン（サムネイル・Shorts
ハイライト・その他目立つ構図のシーン）を`Read`ツールで一通り目視し、
`image_prompt`の意図と明らかに食い違う画像（人物の人数・年代・表情、
時代考証相当の逸脱等）がないか確認する。問題が見つかった場合は、
STEP6.5と同じ要領でユーザー確認なしに`image_prompt`を修正し
`kl_image_gen.py --episode kl{NNN} --scenes {scene_id}`で再生成する。
**同じシーンを2実行しても直らない場合は、それ以上Sonnetメインで再調整を続けず、
ユーザーに確認せずOpusサブエージェントに引き継ぐ**（2026-09-29〜。`kl_image_gen.py`は
1実行の中で自動リトライするため、1実行＝1試行と数える。引き継ぎには、シーンの
`narration`・元の`image_prompt`と修正後の`image_prompt`・QAの指摘・画像のパスを書く。
CLAUDE.md「モデルの使い分けとOpusへのエスカレーション」参照）。

全シーンを1枚ずつ精査する必要はない（KLにはSCの`character_ref`のような
**エピソードを跨いだ**固定キャラクターの参照画像機構は存在しないため、
SCほど網羅的な確認は必須ではない）が、`all_ok: true`だけで無条件にSTEP11へ
進むことはしない。**ただし「エピソードを跨いだ仕組みが無い」ことは
「1エピソード内での主人公の容姿一貫性を確認しなくてよい」ことを意味しない
——この観点はSTEP6.7で別途扱う。**

## STEP 6.7 — 主人公・家族の容姿一貫性チェック（2026-09-11追加）

kl007制作（2026-08-29）で、主人公の髪色が黒髪のシーンと白髪（グレー）の
シーンで混在するという事故が発生した。原因は`image_prompt`に髪色を明記
していなかったため、Gemini画像生成がシーンごとに「単体では"あり得る"が
他シーンとは矛盾する」外見をそのつど選んでしまったこと。同じ回で、ある
シーンが「彼女の家族」とだけ記述していたために、他シーンで明示された
夫（50代）・娘（20代）と矛盾する若い男性＋白髪の高齢女性が生成された
事故も同時に発覚した。ユーザーが目視で気づいた（「主人公の髪型が、黒髪
だったり白髪だったりバラバラ」）まで、STEP6の自動QAはこの種の不整合を
一度も検出できていない。

STEP6.5/6.6のチェックは「1枚の画像がそのシーン単体のimage_prompt・
ナレーションと整合しているか」を見るものであり、**主人公本人の髪型・
髪色・年齢感・体格が、他のシーンに登場する同一人物と一致しているか**
という横断的な同一性は対象外（各シーンが独立して判定されるため、単体で
は自然な外見でも他シーンと矛盾する場合に検出できない）。

**流れ:**
1. 主人公が登場する全シーン（`citation`/`finding`/`data`を除く。CLAUDE.md
   のルール上これらのシーンには主人公が登場しないため対象外）の画像を
   `Read`ツールで並べて確認し、髪型・髪色・年齢感・体格が同一人物として
   一貫しているか確認する。
2. 主人公以外に繰り返し登場する人物（家族・同僚等）がいる場合、同様に
   外見の一貫性を確認する。
3. `image_prompt`側で外見記述が曖昧な箇所（例:「彼女の家族」とだけ書かれ、
   年齢・性別・人数が明記されていない）がないか、JSONのテキストレベルでも
   確認する。
4. 不一致が見つかった場合、該当シーンの`image_prompt`に固定の外見
   descriptor（髪色・髪型・年齢・体格を明記した一文）を追記し、
   `kl_image_gen.py --episode kl{NNN} --scenes {scene_id}`で再生成する。
   以後、そのエピソードの他シーンでも同じdescriptorの文言を使い回す。

### 横断チェックはOpusサブエージェントに委任する（2026-09-29〜）

上記1〜2の画像の横断確認は、以前は「STEP6.6と同じくメインが自分で`Read`して
行えばよく、サブエージェントは不要」としていたが、これを改める。Sonnetメインの
目視では、シーン間の食い違いを見落とす構造的な弱点がある（lamp-whisper LW088で、
同じ玄関ドアの形状・金具が5枚でバラバラだったのをSonnetの目視QAが見落とし、
すべてユーザー指摘で発覚した。kl007・kl016もユーザー指摘まで検出されていない）。
そこで、上記3（JSONのテキスト確認）をメインが済ませたあと、画像の横断確認は
Agent ツール（`model: "opus"`、`subagent_type: "general-purpose"`）に委任する。

**サブエージェントは会話の経緯を持たないため、呼び出し前にメイン会話で
「シーン設定表」を作って渡す:**
```
S03: type=narrative / narration=「…」 / 時代・場面=現在・自宅 / 登場人物=主人公
S07: type=finding / narration=「…」 / 登場人物=匿名の被験者（主人公ではない）
S14: type=impact / narration=「…」 / 時代・場面=未来・自宅 / 登場人物=主人公・夫・統合ロボット
…
一致しているべきもの: 主人公の容姿（descriptorの文言をそのまま書く）、家族の人数・年齢・性別、
  未来パートの統合ロボットのデザイン、impactシーン群の住まい
違っているべきもの: citation/finding/dataの被験者 ⇔ 主人公（kl016の事故）
既に決まっていること: 吹き出しは最初のimpactだけ（2枚目以降は badge_text）、dataシーンは画風が違ってよい（対象外）
```

```
Agent({
  subagent_type: "general-purpose",
  model: "opus",
  description: "kl{NNN} 画像クロスシーン一貫性レビュー",
  run_in_background: false,
  prompt: "
    kagaku-life kl{NNN} の静止画について、同じ人物・同じ物がシーン間で一貫しているか、
    別人であるべき人物が主人公と似ていないかをレビューしてください。まず
    `$HOME/kagaku-life/episodes/kl{NNN}.json` を Read し、次のシーン設定表を前提に、
    `~/Desktop/kagaku-life/images/` の対象シーン画像を Read してください（dataシーンは対象外）。

    {シーン設定表}

    確認観点:
    (A) 一致しているべきもの（主人公・家族・統合ロボット・impactの住まい）が、シーン間で
        髪型・髪色・年齢感・体格・デザインまで食い違っていないか
    (B) 違っているべきもの（citation/finding/dataの被験者）が、主人公と同じ人物に見えないか
    (C) 各シーンの画像が、そのナレーションと時代・場面（現在/未来）に合っているか
    (D) 既に決まっていること（吹き出しの有無など）に反していないか

    指摘は次の2種に分けて報告してください:
    - CRITICAL: 明らかな食い違い（修正が必要）。どのシーンが、どのシーンのどこと食い違うかを
      具体的に。修正の参照に使うべき正しいシーン番号も添える
    - 要相談: 演出上の選択に関わるもの（選択肢も添える）
    矛盾がなければ『問題なし』とだけ報告してください。
  "
})
```

**CRITICALはユーザーに確認せず修正する。** 修正は、上記4のdescriptor追記に加えて、
同一性が正しい別シーンを参照画像にして不一致のシーンだけを1枚ずつ再生成する
（テキストのdescriptorだけでは、独立生成ごとの細部のばらつきが収まらないため）:
```bash
python3 kl_image_gen.py --episode kl{NNN} --scenes 14 --reference-scene 9
```
`--reference-scene`は1回の実行につき1枚で、その実行の全シーンに同じ画像が渡るため、
**不一致のシーンは1シーンずつ別々に実行する**。用途は主人公・家族・統合ロボットの同一性に限り、
構図・背景のコピーには使わない（kl004の判断どおり）。

**再生成の上限:** Sonnetメインでの再生成は同じシーンにつき2実行まで（`kl_image_gen.py`は
1実行の中で自動リトライするため、1実行＝1試行と数える）。2実行で直らなければ、
ユーザーに確認せず、そのシーンの修正をOpusサブエージェントに引き継ぐ（CLAUDE.md
「モデルの使い分けとOpusへのエスカレーション」参照）。Opusでも直らない場合に限り、
STEP11の確認でユーザーに諮る。

**要相談は新しい確認ステップにせず、STEP11のユーザー確認に選択肢付きで含める。**

## STEP 7 — zoom_anchor判定・カメラワーク自動決定（実行タイミングに注意）

**このSTEPはSCと完全に同じ仕様で、全シーンの`ken_burns`を判定結果で
上書きする（2026-08-25確定）。** STEP2でシーンJSONに書いた`ken_burns`
（`zoom_in`/`zoom_out`/`pan_left`/`pan_right`/`static`）は、このSTEPの
実行によって必ず以下のいずれかに上書きされる（SCの`infer_zoom_anchor()`が
`character_ref`の有無だけで機械的に決めるのと同じ）: 1人構図→`zoom_in`、
2人構図→`pan_zoom_out`、0人/3人以上→`zoom_out`。結果として`static`/
`pan_left`/`pan_right`は実質使われない。STEP2でのシーン生成時、`ken_burns`
の値をあまり神経質に選ぶ必要はない（どうせ上書きされるため）。

**このSTEPの実行は、STEP11で画像・ナレーション・BGMのユーザー確認がすべて
OKになった「後」まで待つこと（2026-08-25改訂）。** zoom_anchorは静止画の
主被写体位置を判定してKen Burnsの焦点をJSONに書き込む処理のため、レビュー
段階で画像が差し替えになった場合、レビュー前に実行すると無駄になる
（差し替えのたびに再実行が必要になる）。ユーザーから当初「画像とナレーション
は同じタイミングで確認するので、レビュー前のzoom_anchor実行は不要」と
指摘があり、その後「画像・ナレーション・BGMの確認OKでzoom_anchorに進む
ように」とBGMも含めるよう明示された。BGM（STEP10）はSTEP9の後・STEP11の
前に位置しているため、実行順序自体は変わらない——STEP11のゲートが
画像・ナレーションの2つからBGMを含む3つに増えた、という変更。

実行コマンドは以下（STEP11「OKが得られたら」の直後、`kl_finalize.py`より前に
実行する）:

```bash
python3 kl_zoom_anchor.py --episode kl{NNN}
```

## STEP 10 — BGM選定

CLAUDE.md「BGMパイプライン」の手順に従う（トーンは必ず温かく・希望が持てる・
押し付けがましくない。禁止語: epic/battle/war/dark/aggressive/horror）。

**SC/LWと同じく、候補は「Freesound新規ダウンロード」だけでなく「`bgm_library.json`
の既存曲」も含めて役割ごとに揃える。** 過去エピソードで確認済みの曲は品質・
トーンの信頼度が高く、新規ダウンロードだけに頼ると同じ探索を毎回繰り返すことになる。

1. `bgm_library.json` を読み、役割のトーン（intro=好奇心・静かな導入、
   main=研究紹介への高まり、outro=温かい余韻）に近い`tags`を持つ既存曲を
   役割ごとに1〜2曲ピックアップする（同一エピソードでの重複使用は避ける）。
2. Freesoundから役割別（intro/main/outro）に新規候補を1曲ずつダウンロード:
   ```bash
   mkdir -p "$HOME/Desktop/kagaku-life/BGM"
   FREESOUND_API_KEY=$FREESOUND_API_KEY python3 "$HOME/lamp-whisper/freesound_download.py" \
     "<Q_intro>" "<Q_main>" "<Q_outro>" \
     "$HOME/Desktop/kagaku-life/BGM/" \
     --round 0 --start-slot 1 \
     --library "$HOME/kagaku-life/bgm_library.json"
   ```
3. 新規ダウンロード分のみ `kl_bgm_qa.py --dir` でボーカル混入チェック
   （ライブラリ曲は過去のQA実績があるため再チェック不要）
4. 役割ごとに複数候補（ライブラリ+新規）がある場合、Claudeがテキスト情報
   （曲名・タグ・QAの音の説明）だけで1曲に絞り込む
5. `kl_bgm_final_check.py --episode kl{NNN}` で実音声+制作確認書をGeminiに渡し、
   最終検証（テキストだけでは質感を見誤ることがあるため省略しない）
6. 条件付き採用・差し替えが出た場合は該当役割だけ差し替えて再検証する
7. 承認が得られたら本登録する:
   - 新規曲の場合: `kl_bgm_library.py --add --episode kl{NNN} --role {role} --file {path} --stem {name}`
     （Google Driveへ移動・`bgm_sources`に記録・ライブラリに新規追加）
   - 既存ライブラリ曲を採用した場合: `kl_bgm_library.py --use-library --episode kl{NNN} --role {role} --stem {library_id}`
     （ダウンロード・移動不要、`bgm_sources`に既存パスを記録・`used_in`を更新）
8. CC BYライセンス曲があれば `kl_inject_bgm_credit.py --episode kl{NNN} --credit-file {path}`
   でクレジットを概要欄に注入

## STEP 12 — 動画生成

**動画生成前に、想定尺（STEP2で見積もった値、または実際のナレーション音声長
合計）が7分を大きく下回りそうな場合は、尺を伸ばすかどうかユーザーに確認する**
（STEP2の「想定尺の見積もり」参照）。

```bash

```

引数なしで本編（`kl{NNN}.mp4`）とShorts（`kl{NNN}_shorts.mp4`）の両方が
生成される（Shortsのみ再生成したい場合は `--shorts-only`、本編のみは
`--no-shorts`）。

完成後、複数箇所（本編: ティザー・本編冒頭・本編中盤・
ロゴアウトロ、Shorts: 冒頭・中盤・末尾）をフレーム抽出して目視確認し、
STEP9に記載のテロップ不具合（単語途中分割・一瞬で消えるカード・シーン境界の
重複）がないかも合わせて確認する。`SendUserFile` でユーザーに送る。
フィードバックがあれば該当工程（画像/音声/テロップ/動画生成）に戻って修正し、
**修正後は必ず `kl_finalize.py` でGoogle Driveへ同期してから
`kl_video_gen.py` を再実行する**（`kl_video_gen.py`はGoogle Drive側の素材を
読むため、Desktop側の修正だけでは反映されない。kl001制作時に実際にこれが
原因で修正が反映されない事故が起きている）。

**テロップの描画設定（フォント・縁取り太さ・色等）は `kl_telop_gen.py` と
`kl_video_gen.py` の両方に別々の実装があり、片方だけ直すと反映漏れが起きる
（kl001制作時に実際に発生）。テロップの見た目を変更する際は両ファイルを
同時に修正すること。**

**動画の確認が済んだら、`kl_finalize.py` を再実行して完成動画をGoogle Driveへ
同期する（2026-08-30追加）:**

```bash
python3 kl_finalize.py --episode kl{NNN}
```

**このSTEPの実行を忘れないこと。** `kl_video_gen.py`の出力
（`~/Desktop/kagaku-life/output/kl{NNN}.mp4`・`kl{NNN}_shorts.mp4`）は
ローカルのDesktopに書き出されるだけで、STEP11で行ったDrive同期には含まれて
いない（STEP11時点ではまだ動画ファイルが存在しないため）。`/kl-upload`
（`kl_sns_up.py`）はGoogle Drive `Kagaku-Life/KL{NNN}/output/`から動画を
読むため、ここでfinalizeを再実行しておかないと、後日`/kl-upload`実行時に
「本編動画が見つかりません」で失敗し、その場で`kl_finalize.py`を慌てて
再実行する羽目になる（kl007・kl008で実際に2回連続発生した）。
