# /kl-new — くらしを変える科学 新エピソード制作

論文選定（STAGE1〜5）からエピソードJSON生成・動画完成までの全工程を実行するコマンド
（2026-08-24、`/kl-topic`を統合。旧`/kl-topic`は廃止し、このコマンド1つに一本化した）。
**2026-10-04から掛け合い形式（固定の二人、`cast.json`）。旧形式（kl001〜kl030）のルールは
`legacy/kl-new_monologue_until_2026-10-03.md`。** 各ステップは人間の確認を挟みながら進める（SCの`sc-new.md`と同じ設計思想: 重い創作ステップは
サブエージェントに委任し、オーケストレーター＝この会話はスクリプト実行と検証・進行管理に
専念する）。

> 論文選定（STEP1のSTAGE1〜5）は2026-08時点では軽量版。STAGE5の判断基準（「動画にしやすさ」
> 等の実務観点での選び直し）はまだパターン化できていないため、都度の会話に委ねる。何周か
> 運用して判断パターンが固まってきたら、このコマンドに反映していく。

## STEP 0 — 最新の状態にする（2026-10-16〜、毎回最初に実行）

夜間のニュース採点（GitHub Actions、毎日04:00 JST）が `news_candidates.json` を main に push しているので、作業の前に必ず取り込む。
会話が長くなっているときは、先にユーザーに **`/clear` を勧める**（`/clear` はコマンドの中から実行できない。会話の経緯は
`CLAUDE.md`・この手順書・`MEMORY.md`・`topics_queue.json`・エピソードのJSONにあるので、消しても制作は続けられる）。

```bash
hostname                      # マシン判定（CLAUDE.md「マシン判定ルール」）
git status --short            # 未コミットの変更が残っていないか確認（あれば内容を見てから進める）
git pull --rebase             # 夜間の採点・他のマシンの変更を取り込む
git log --oneline -5          # 直近の変更を一目で確認
```

- 競合したら、無理に解消せずユーザーに状況を報告する（夜間の自動コミットは `news_candidates.json` だけを書き換える）
- 夜間の採点が今朝分まで入っているかは、ケースCの冒頭の手順（`buzz_measured_at` が直近24時間以内か）で確かめる

## STEP 1 — トピックを確定する

`topics_queue.json` の `queue` 配列に、先頭に `status: "confirmed"` のエントリがあるか確認する。

### ケースA — 既に確定済みトピックがある場合

そのエントリを次のエピソードとし、`episode_id`・`title`・`entry_question`（視聴者側の問い）・
`references`（複数可）・`notes`（構成テンプレート・予想される判定・ツッコミの材料）をユーザーに要約提示し、
この内容で進めてよいか確認する。OKが得られたらSTEP2へ進む。

### ケースB — 確定済みトピックがない場合（関心ごとの選定から開始。2026-10-04からはケースCのニュース起点が既定の入口）

2026-09-29に「論文のプールを採点して上位から選ぶ」方式から「視聴者の関心ごとから入り、
その関心ごとに答える論文を探す」方式へ作り直した（経緯・根拠は `PIPELINE_REDESIGN.md`、
`docs/paper_selection.md`「論文選定ロジック」）。以下のSTAGE0〜5を順に実行し、`topics_queue.json` に
新規`confirmed`エントリを追記してからケースAの手順に進む。

#### STAGE 0 — 次に扱う関心ごとを決める

```bash
/usr/bin/python3 kl_concern_select.py
```

直近の回と `viewer_concerns.json` の選定ルールから、この回で使える枠（健康系・ワイルドカードの
残り）と、選べる関心ごとの上位3件（当事者の広さ・前回からの間隔の順）が出る。これをそのまま
ユーザーに提示し、どの関心ごとにするかを決めてもらう。

- 提案以外の選べる関心ごとも見たい場合は `--all` で全一覧を出す
- 健康系の枠が埋まっている回は、健康系の関心ごとは提案に出てこない（スクリプトが除外する）
- ワイルドカード枠が残っている回は、関心ごとの代わりに**ワイルドカード回**
  （関心ごとを持たず、意外性・感動で選ぶ回）にすることもできる。その場合は下の
  「ワイルドカード回の手順」へ進む
- 関心リストに無いが扱いたい関心ごとをユーザーが挙げた場合は、根拠（公的統計・検索候補など）を
  確認したうえで `viewer_concerns.json` に追加してから進める

#### STAGE 1 — 論文を集める（関心ごと単位）

`topics_shortlist.json` に、その関心ごと（`concern_id`）の `status: "available"` が
**3件以上**あれば、検索は省略してSTAGE2へ進む。その前に必ず採点バージョンのゲートを通す:

```bash
/usr/bin/python3 kl_shortlist_rescore.py --check
```

非ゼロ終了なら `kl_shortlist_rescore.py --concern {id}` で再採点してから提示する。
`--check` が「既視感判定が最新エピソードを見ていない」と警告した場合は、直近の回と同じ型の候補が
既視感なしのスコアのまま残っている前提で読み、必要なら `--stale-deja-vu` で再判定する。

3件未満なら、次を順に実行する（Semantic Scholarの検索とGemini呼び出しを伴う）:

```bash
/usr/bin/python3 kl_paper_search.py --concern {id}
/usr/bin/python3 kl_paper_triage.py --concern {id}
/usr/bin/python3 kl_paper_screen.py --concern {id}
/usr/bin/python3 kl_venue_allowlist_update.py
/usr/bin/python3 kl_paper_hypecheck.py --concern {id}
/usr/bin/python3 kl_paper_interest_score.py --concern {id} --top 10
/usr/bin/python3 kl_shortlist_add.py
```

- `kl_paper_triage.py`（STAGE1.5）は、検索で集まった数百〜数千件をタイトルとアブストラクト冒頭だけで
  まとめて判定し、「その関心ごとを持つ一般の人への答えになりそうか」の上位40件だけをSTAGE2へ送る。
  関心ごと起点の検索は旧カテゴリよりヒット件数が桁違いに多く（実測: 睡眠で2,664件）、STAGE3・4を
  全件に回すと時間もコストも見合わないため。被引用数は使わない
- `kl_venue_allowlist_update.py` は提案のみ行う。提案された掲載誌をユーザーに見せ、追加してよいか
  確認してから `--apply` で反映する（低品質誌を誤って許可リストに載せないため）

関心ごとごとに簡潔な件数サマリのみ報告する（生データは画面に出さない）:

```
[{関心ごと}]
STAGE1: 収集{N}件 → プレフィルタ通過{N}件（うちプレプリント{N}件）
STAGE1.5: 上位{N}件をSTAGE2へ（最低点{N}）
STAGE2: pass={N}（うち許可リスト自動pass{N}） flag={N} exclude={N}
STAGE3: ok={N} caution={N} high_risk={N}
STAGE4: 上位{N}件をランキング
```

#### STAGE 2 — 候補を提示する

`topics_shortlist.json` のその関心ごとの `available` 候補を、総合スコア順に上位5〜10件提示する。
各候補について次を見せる:

- **視聴者側の問い**（`entry_question`）と総合スコア
- スコア内訳。特に `wonder_score`（最重要）・`answer_fit_score`（その悩みに本当に答えているか）・
  `applicable_breadth_score`（当てはまる人の広さ）は単独の数値として見せる
- `debate_score`（議論を呼ぶか・二人の判定が割れそうか、2026-10-04〜）、`expected_verdicts`（予想される二人の判定）、
  `tsukkomi_material`（ツッコミの材料）。掛け合い形式では、夢とツッコミの両方の材料がある研究ほど台本が面白くなる
- `evidence_level`（ヒトの試験か、動物実験だけか等）。動物実験・細胞だけの研究は答えの適合度が
  コード側で2点以下に抑えられている
- `market_status`・`novel_delta`（市場に既にある部分と本当に新しい部分）、`future_scene_sketch`
- `behavioral_familiarity: familiar` と `deja_vu_level: strong` のラベル（どちらもwonder/transformationが
  コード側で上限3にキャップされている。ラベルを見せずにスコア順に並べない）。`deja_vu_note` が
  空でない候補は指摘内容を明記する（除外はせず判断材料として見せる）

同じ技術の型の候補が3件以上上位に来ている場合は、その型からは上位2件までを提示し
「他に◯件、同種の候補あり」と注記する。

#### STAGE 2.5 — ストーリー案を2〜3案提案する

上位候補から、実際にどの論文（複数可）でどんな回にするかを2〜3案提案する。各案に含めるもの:

- **視聴者側の問い**（タイトルとShortsのフックの土台になる。論文が示した範囲を超えて一般化しない）
- **使用する論文**（複数本なら組み合わせる必然性）
- **構成テンプレート**（basic／verdict_first／myth_buster、STEP2）と、**予想される判定**（大輔・沙織それぞれ）
- **ツッコミの材料**（論文本文から: 被験者数・試行回数・比較相手・著者が書いている限界）と、**中盤で裏切れそうな数字**
- **大輔が置く使い道（`use_case` の候補）と、それに答える一次資料**（例: 「月末の経理を任せたい」→ 画面操作のテストの点数。
  2026-10-17〜、構成 v3。旧「夢語りが描く生活の一場面」は廃止）
- **なぜ面白いか**（wonder・答えの適合度・当てはまる人の広さとの対応）

#### STAGE 3 — 既知のパイプラインギャップを踏まえて補足する

`docs/paper_selection.md` STAGE2に記載の通り、Semantic Scholarがプレプリント版と正式出版版を別レコードとして
統合していない場合、優れた論文がSTAGE1の自動探索から漏れることがある（kl002の実例）。
ユーザーが「他にこういうテーマはないか」と聞いてきた場合や、上位候補の質に納得できない場合は、
WebSearchで補助的に探してよい。査読済み掲載であることを出版元の公式ページURLで人間が直接確認
できれば、`pipeline_gap_flag: true` を付けて候補に加えられる。

#### STAGE 4 — 人の最終ゴーサイン

提案したストーリー案（または修正案）のどれで行くかをユーザーに確認する。「動画にしやすさ」
（統計的ヘッジの複雑さ、絵作りのしやすさ、主人公の物語の組み立てやすさ）も踏まえて一緒に検討してよい。
あわせて、直近5話程度の**実際の内容の型**（研究の型・アプローチ）が連続していないかも確認する
（`docs/paper_selection.md` STAGE5「カテゴリのローテーションだけでは内容の型の偏りを検出できない」）。

#### STAGE 5 — topics_queue.jsonに追記する

確定した回を `topics_queue.json` の `queue` 配列末尾に追記する。

- `episode_id`: 既存の最大値+1（`kl{NNN}`）、`status`: `"confirmed"`
- `slot_type`: `"concern"`（関心ごと起点）／`"wildcard"`（ワイルドカード回）
- `concern_id`: 関心ごとのid（ワイルドカード回は近いものがあれば記入、無ければ `null`）
- `genre`: 5ジャンルのどれか（`ai`/`humanoid`/`medical`/`food_health`/`life_tech`、定義は `genres.json`）。**再生リスト・公式サイト・ニュース提案の分類の正**（2026-10-06〜）。迷ったら `genres.json` の `rules.classify`（驚きの中心がAIの能力ならai、成果が薬・食品なら medical/food_health、ロボットは人の形かだけで humanoid/life_tech）
- `health`: 健康系の回として数えるか（true/false）。ヒトの体・病気・毎日の調子・老化・食と健康の研究紹介なら true。動物の医療・食の技術・ロボットやAIの能力が主役の回は false（`genres.json` の `rules.health`）。5話に2話までの上限はこの印で数える
- `domain`: 関心ごとの領域（`body`/`disease`/`daily`/`life`、履歴・分析用。分類には使わない）。ワイルドカード回も内容に近い領域を
  1つ入れる（健康系の上限の判定と公式サイトの分類に使う）
- `entry_question`: 視聴者側の問い
- `title` / `format` / `references[]`（`title`/`authors`/`year`/`venue`/`url`または`doi`/`is_preprint`/`institution`） /
  `hook_idea` / `notes`（構成テンプレート・予想される判定・ツッコミの材料。2026-10-04から `protagonist` は持たない）
- `stage4_snapshot`: 採用した論文の選定時点のSTAGE4スコア（在庫の該当エントリから
  `overall_score`・`score_breakdown`・`evidence_level`・`market_status`・`novel_delta`をコピー）。
  事前の採点と実際の視聴データが合っていたかを後で `/kl-analytics` で検証するため
- `pipeline_gap_flag: true` の候補を採用した場合はその旨と根拠を `notes` に明記する

採用した論文の在庫エントリ（`paperId` で照合）を `status: "used"`・`used_in: "kl{NNN}"` に更新する
（ワイルドカード回で旧在庫から採用した場合は `topics_shortlist_legacy.json` 側を更新する）。

**単に今回選ばれなかった候補（`available` のまま、削除しない）と、ユーザーが明示的に
「既視感がある」「面白みに欠ける」等の理由で却下した候補（`status: "rejected"`・
`rejected_reason` に理由）を区別する。** 却下を記録しないと、次回以降も同じ候補が提示され、
既視感の判定（`kl_paper_interest_score.py` の `build_past_episodes_context()` が却下済みを
参照する）も機能しない。ユーザーが候補を明示的に否定した発言は、その場でこのステータス更新に
反映すること（STAGE5の追記時だけでなく、STAGE2〜4の途中でも）。

追記後 `total_topics` と `last_updated` を更新する。コミットメッセージには選定理由を残す。
追記後、ケースAの手順（要約提示・確認）に進み、OKが得られたらSTEP2へ進む。

### ケースC — ニュース起点の回（2026-10-04〜、既定の入口）

**夜間実行（2026-10-14〜）:** 毎日 04:00 JST に GitHub Actions（`.github/workflows/nightly-news.yml`）が collect〜buzz〜list を済ませ、
`news_candidates.json` を main に push し、ベスト3の下書きを Slack に送っている。朝は先に `git pull` し、`news_candidates.json` の
`buzz_measured` の計測時刻が当日（直近24時間以内）なら **collect〜buzz を飛ばして `list --top 10 --check-urls` から始める**
（二重の待ち時間と課金を避ける）。古い・無い場合だけ、下の手順を最初から実行する。夜間分は機械的な下書きなので、既視感・競合動画・
ジャンルの間隔・一次資料の確認はこれまでどおりこの会話で仕上げる。

**ニュースが入口、一次資料が答え合わせ。** 関心ごと起点で見つかる論文は1年〜数年前のものになりがちで、AI分野の
進み方から見ると古めかしく「どこかで聞いた話」になる、というなるさんの判断で加えた。論文起点（ケースB）も残すが、
検索範囲は直近6か月に絞った（`kl_paper_search.py --months 6` が既定）。

```bash
/usr/bin/python3 kl_news_scan.py collect --days 21   # RSS（news_sources.json）＋Gemini検索で直近の発表を集める
/usr/bin/python3 kl_news_scan.py score --top 15      # 一次資料を探させて採点（検索つき、1件ずつ課金）
/usr/bin/python3 kl_news_scan.py verify               # 一次資料URLの実在確認（HTTPだけ・無料。DOIはハンドルAPI。2026-10-15〜）
/usr/bin/python3 kl_news_scan.py repair [--id ID ...] [--force]   # 404の一次資料の正しいURLを探す（HTTPだけ・無料。2026-10-15〜）
```

| お題と予想 | `setup` | お題＋二人の最初の予想（`prediction`、二人とも） | 固定背景 `base_cafe_b` | intro |

**v3 の規則（`kl_dialogue.py check` が確認する）:**
- 必須タグ: `question`・`weakness`・`barrier`（従来どおり）＋ `use_case`・`takeaway`。**`life_scene` は必須ではない**
- `use_case`: **大輔（dreamer）の台詞**に付ける。**論点ラウンドの中**（`round` のあるシーン）に置き、**同じ論点のそのシーン以降に
  `check`** があること（使い道を資料に当てる）。1話に1つ以上（論点ごとに1つが目安）
- `takeaway`: **`verdict` シーン**の台詞に付ける。どちらが言ってもよい。「誰が・何に・どんな条件で／いつ」を具体的に
- `dream`: **任意・1話に1つまで。** 置くのは、現物がまだ無く絵で見せる価値があるとき（ヒューマノイドの試作機が現場に来る、
  臨床試験前の治療など）だけ。v2 の画像の規則（年齢・容姿を決めた人物を描かない）を引き継ぐ。`life_scene` を使うなら dream の中だけ
- 常套句（v3 で追加）: 「言い直す／言い直し」0回、「想像してみてよ」1回まで（dream を置く回だけ使う）
- 警告（⚠、不合格にはしない）: 沙織が譲る `turn`（大輔が正しかった論点）が無い。STEP5 で見る

**`use_case` の書き方（「使い道を1つ置く → それに資料が答えられるか」）:**
- 使い道は、視聴者が自分に置き換えられる具体的な作業にする。主語は「僕なら」「たとえば小さな会社の経理なら」の仮定でよい
  （年齢・容姿・名前を決めた人物を作らない。二人の経歴を足すなら「〜としたら」の仮定）
- 置いた使い道を、**次の行かすぐ後の `check` で一次資料に当てる**。資料が答えられないなら「この資料では分からない」と言う
- 例（kl042 を v3 で書くなら）:
  > 大輔［use_case］「僕なら、月末の経理に使う。請求書の画面を開いて、数字を表に写して、送るところまで」
  > 沙織「それは画面の操作ね。総合1位とは別の物差し。ヴァルズのページに、画面とマウスだけで操作するテストがある」
  > （check: 資料カード）沙織「どのモデルも20点未満。アルゴンは4.83%で、トップでもない」
  > 大輔「じゃあ経理の画面操作は、まだ任せられない。任せるなら、資料を読んで下書きを作るところまでだ」（turn）
- 例（大輔が勝つ論点）: kl041 S07〜S08 のように、大輔が会社側の資料（技術ブログの比較表）を持ってきて、
  沙織の「比べられたら困るんじゃないの？」が外れる。毎回大輔が論破されるだけの回にしない
- 未来の場面を「想像してみてよ」で描いて崩し、「言い直す」でもう一度描く型は使わない。言い過ぎを直すときは、
  **使い道の範囲を狭める**（「全部任せる」→「下書きまで」）形で、その論点の中で着地させる

**`takeaway` の書き方:** 判定ラベルを「自分ごと」に落とす一文。例「長い資料や動画を読んで下書きを作る机の仕事なら、
有料プランで、確かめながら、もう使える」「ヒトで確かめるまでは、食べ方を変える理由にはならない」（健康の話題は
視聴者への助言にしない。「研究の紹介で、おすすめではない」の線は従来どおり）。

**画像:** dream を置かない回は、AIで生成する挿絵が v2 よりさらに1〜2枚減る（目安4〜6枚）。挿絵は話題の実物
（製品・機体・実験・使われる場所）にする。使い道の場面を絵にするなら、v2 の dream と同じく人物を描かない（手元・物・場所）。

**BGM:** dream が無くても intro→main→outro の順は変わらない。intro=ティザー＋お題、main=論点ラウンド全部、outro=判定と締め。
dream を置く場合は論点の中なので `bgm_role: "main"` を明示する（type の既定値は intro のため）。

### 構成 v4「実現ラウンド」（2026-10-26〜、kl049 から。`"structure": "rounds_v4"`）

**新しい回はこの構成で書き、トップレベルに `"structure": "rounds_v4"` を付ける。** 上の v2・v3 の規則（予想・論点ラウンド・資料カード・
`use_case`・`takeaway`・dream は任意で1つまで ほか）はすべてそのまま有効。`kl_dialogue.py check` が v2・v3・v4 の規則を全部確認する
（v4 の指摘は「v4:」と出る）。v3 と食い違う箇所は v4 が優先。設計と診断の数字は `DIALOGUE_REDESIGN_2026-10-26.md`。

**なぜ変えたか（2026-10-26、なるさんの指摘「沙織の意見が強くて、結局は夢を潰す感じになる。視聴者に夢を与えることにならない」）:**
kl031〜kl048 の18話で、沙織の判定は12話が後ろ向きの札（まだ眉唾9・根拠待ち4のうち）、二人とも「もうすぐ来る」は3話だけ。kl048 では論点ごとに
「大輔が夢を出す → 沙織が資料で削る → 大輔が『こう狭める』『いきなり危ない』と夢を小さくする」がくり返され、論点の最後の一言は
「まだ測っていない」だった。原因は性格ではなく仕組み: 問いが「本当か？（盛っていないか）」という検査になっていた、論点の終わり方の規則が
無かった、判定の札が盛った発表の主張をそのまま裁いていた、ネタ選びが誇張を加点していた。

**問いを変える:「本当か？」→「どこまで来た？ どうすれば使える？」。** 夢は潰すものではなく、資料で確かめて育てるもの。
誠実さ（資料の範囲を超えない、捏造しない、健康の助言をしない、査読前の開示）は変えない。変えるのは、資料を伝える順番と終わり方。

**1話の流れ:**

| 区間 | type | 中身 | 画面 | BGM |
|---|---|---|---|---|
| ティザー | `teaser` | 一番わくわくする事実＋一番の壁（壁だけで終えない） | 本編の挿絵を流用 | intro |
| お題と予想 | `setup` | 大輔「（発表がもう決めている使い道を事実として言ったうえで）次は、ここにも広がる」／沙織「本物なら使いたい。そのために、ここを確かめたい」（`prediction`、二人とも）。沙織の予想は「盛ってる」ではなく「確かめたい条件」で言う | 固定背景 `base_cafe_b` | intro |
| 論点1〜3 | `paper` `check` `tsukkomi`（`dream` は任意） | **夢・使い道（`use_case`）→ 壁（沙織の資料）→ 越え方（`workaround`）→ 残った手応え（`hope`、論点の最後の行）** | 資料カード／図／挿絵 | main |

**v4 の規則（`kl_dialogue.py check`）:**

| 規則 | 扱い |
|---|---|
| 各論点の最後の行（次の論点・判定の前）に tag `hope`（残った手応え: 資料で確かめられた、前向きに使える事実） | ❌ |
| 各論点に tag `workaround`（壁の越え方: 条件・使い方・待てば変わること。資料に無ければ「何が確かめられたら越えられるか」）が1つ以上 | ❌ |
| 沙織の tag `skeptic_wish`（「本物なら、私はこれに使いたい」）が1話に1つ以上 | ❌ |

| tag `next_step`（視聴者が今日・今月できる一歩）が `verdict` か `closing` にある | ❌ |

1行に付けられるタグは1つ。`hope` の行は論点の最後なので、`turn` と重なるときは `turn` を一つ前の行に置く。

**判定の札は1組（2026-10-26。同日に「2組（使い方の札＋発表の言い方の小さな帯）」で始めたが、kl049 の初見レビューで毎回「追いにくい」と指摘され、なるさんの「分かりやすくしよう」で1組に戻した）:**
- 画面に出す札は `verdict` だけ。対象は、二人が論点で育てた使い方（誰が・何に・どんな条件で／いつ）。札の出し方は従来どおり（同じなら1枚、割れたら「大輔の判定」「沙織の判定」の2枚）
- 発表の言い方（お題の主張）は、判定の場面の台詞で一言だけ触れる。**札の言葉（もうすぐ来る・3年はかかる 等）を使わない**（二つの判定が混ざって聞こえるため）。例「先に言っておくと、発表そのものは控えめで、10月から動き出すのも本当。判定するのは、その先」「発表は『全部任せられる』と言ってるけど、資料はそこまで言ってない。判定するのは、この使い方」
- `claim_verdict` は記録用に JSON に残す（画面には出さない。発表の言い方に対する二人の見立てを、後で振り返るため）
- 札の文言・色・キー（`soon`/`decade`/`pending`/`dubious`）と使い分けの決まり（CLAUDE.md）は変えない

**論点の書き方（kl048 を v4 で書くなら）:**
> 大輔［use_case］「各社の例は秘書の仕事。次は、うちみたいな小さな会社の月末にも使える。出し忘れの請求や、返事をしていないメールに気づいてもらう」
> （check）沙織「待ち時間を短くして、一度に出す数も増やしたら、先回りを好んだ人は47%。『気が散る』という声も出た」
> 大輔［workaround］「だったら、思いつくたびに割り込ませない。月末に一度、まとめて持ってきてもらう」
> 沙織「それは、この実験の向きと合う。ゆっくり控えめに出した作り方だと、8割以上が先回りを喜んだ」
> 大輔［hope］「控えめに出せば、8割が喜ぶ。月に一度まとめて、なら今日から頼める」

- 限界（「毎日の暮らしで何週間も使った資料は無い」など）は言ってよいが、越え方の前に言い終える。論点の最後に置かない
- 大輔は削られても「狭める」「危ない」で引かない。「だったら、こう使う」と条件をつけて前に進む（夢の大きさは条件つきで残す）
- **`use_case` は発表のその先に置く（2026-10-26、なるさんの指摘「『僕なら、これに使う』が毎回すこし違和感ある。会社はすでにそのような想定で開発してるし、そのように使ってる」）。** 発表元がもう決めている使い道・すでに使っている用途を、大輔が「僕なら」で自分の思いつきのように言い直さない（kl049 の初稿は、JR西日本がすでに使っている「電線の近くの高い所の作業」を「僕なら、これに使う」と言っていた）。すでに決まっている使い道は事実として言い、大輔の期待はその一歩先（別の業種・別の作業・視聴者の店や会社・まだ発表が言っていない条件）に置く。その一歩先を、論点の資料で確かめる。発表がまだ使い道を言っていない新技術なら、大輔の思いつきでよい
- 口癖「僕なら、これに使う」は v4 では使わない（`kl_dialogue.py check` が検出する）。新しい口癖「次は、どこで使える？」は1話に1回まで。決まり文句にせず、使うなら発表の範囲を確かめ終えて次へ進む場面で
- 沙織の `skeptic_wish` の例:「これが本物なら、私は研究室の会議の議事録に使いたい。だから、話者の聞き分けの精度を確かめたい」
- 答え合わせの資料を沙織だけが持つ形にしない。大輔も第三者の評価・使った人の声・数字を持ってきて、沙織が「そこは私の読み違い」と認める論点を作る

**`next_step` の書き方:** 視聴者（50〜60代、経営者・商売人が多い）が今日・今月できる一歩を1つ。例「まずは無料の範囲で、返事を出し忘れた
メールを探させてみる」「送る・払うは自分で押す設定のまま試す」「来年の春、使った人の声が出そろってから決める（何を見ればいいかも言う）」。
投資判断・健康の助言にはしない（健康の回は「研究の紹介で、おすすめではない」の線のまま。「次の受診で聞いてみる」程度にとどめる）。

**エピソードJSON:** トップレベルに `"structure": "rounds_v4"` と `"claim_verdict": {"dreamer": "...", "skeptic": "..."}` を足す。`verdict` は使い道への札。

### 生成ルール

**動画尺（2026-10-18改訂、なるさんの指示）:** **最優先は「ちゃんと伝わる・分かりやすい」こと。尺はそれに合わせて最適化した結果で、
6分・7分・9分といった尺・字数・シーン数の制約に引っ張られない。** 説明が必要なら必要なだけ足し、冗長なら削る（短くなる回があってもよい）。
`kl_dialogue.py check` が出す目安の尺（実測はおおよそ290〜340字/分）は、書いたあとに測って報告するだけで、削る・足す理由にしない。
「伝わるか」は、資料を見ていない初見の視聴者の目で台詞だけを読むレビュー（STEP5.5、必須ゲート）で確かめる（初出の専門用語に言い換えがあるか、
主語・指示語が省かれていないか、前に出ていない発言を引用していないか、たとえ話の論理が原典と合うか、キーワードを最初に定義したか）。

**シーンの種類（`scene.type`）と、BGMの役割の既定値:**

| type | 内容 | 画風 | BGM役割の既定 |
|---|---|---|---|
| `teaser` | 冒頭の問いと先出し（3〜4カット、1カット1行、各30字以内） | 物語調 | intro |
| `setup` | 今日の問い、身近な困りごと、または通説 | 物語調 | intro |
| `paper` | どんな研究か（大学名・発表年・方法・結果） | 物語調（研究室） | intro |
| `dream` | 未来の一場面（v3 では任意・1つまで。現物がまだ無い回など） | 物語調（未来） | intro（v3 で論点の中に置くなら main を明示） |
| `tsukkomi` | ツッコミ: 一番の弱点・実用化までの壁 | 物語調 | main |
| `check` | 答え合わせ: データで確かめる（グラフ・比較図） | チャート調 | main |
| `verdict` | 判定（1話に1つ） | 固定背景 `base_cafe` | outro |
| `closing` | 締め・CTA | 固定背景 `base_cafe` | outro |

- **並び順は固定しない。** 下の構成テンプレートから話ごとに選ぶ。ただし `teaser` は冒頭にまとめ、`closing` を最後にする
- **BGMは `scene.bgm_role`（intro/main/outro）で切り替わる。** 本編の並びで intro→main→outro の順に後戻りさせない
  （type の既定値と違う並びにするときは、各シーンに `bgm_role` を明示する。例: ツッコミの後の2本目の `paper` は main、
  後半の `dream` は main か outro）。intro=好奇心・導入、main=軽い緊張感（ツッコミ・答え合わせ）、outro=判定と余韻
- `verdict` と `closing` は `"image_asset": "base_cafe"`（二人がいつも話題を持ち寄るカフェの固定背景、`assets/base_cafe.png`）
  を使う。毎回同じ場所に戻ってくることで、番組の「ホーム」を作る。**固定背景は2種類（2026-10-14〜）:** `verdict` は `base_cafe`
  （窓側の席）、`closing` は `base_cafe_b`（同じカフェをカウンター側から見た別角度、`assets/base_cafe_b.png`）。判定と締めで
  約75秒同じ絵が続くのを避けるため（なるさんの指摘）。`closing` に `"image_asset": "base_cafe_b"` を書く

**構成テンプレート（`template` に記録する。直近の回と同じテンプレートが3回続かないようにする）:**

- **`basic`（基本）**: 問い → 主張・使い道 → ツッコミ → 答え合わせ → 判定（v3。kl040 までは「問い → 夢 → …」、kl031が実例）
- **`verdict_first`（結論先出し）**: teaser・setup で判定を先に言い、なぜそうなるかを掛け合いで解く。冒頭に
  「でも、面白いのはそこじゃない」のような回収すべき約束を置き、後半で回収する。kl032が実例
- **`myth_buster`（通説くずし）**: setup で常識・通説を出す → それを覆す研究結果（paper/check）→ ツッコミ → 使い道 → 判定

**必ず入れるもの（`lines[].tag` で印を付ける。`kl_dialogue.py check` が確認する）:**

- `question`: 視聴者側の問い（`entry_question`）を言い切る行。teaser の中に置く
- `life_scene`（kl042 まで必須。**v3 では任意**で、使うなら dream の中だけ）: 大輔が描く具体的な生活の一場面
- `use_case`・`takeaway`（**v3 で必須**）: 上の「構成 v3」を参照
- `weakness`: ツッコミが言う**この研究の一番の弱点**。数字・条件を伴わせる（被験者数、試行回数、動物実験止まり、
  計算値か実測か、比較相手、条件の狭さ）。ツッコミの台詞に付ける
- `barrier`: ツッコミが言う**実用化までの壁**（論文自身が書いている限界を優先。コスト・規制・安全など論文外の一般論を
  言う場合は「研究の外の話だけど」と区別する）

**掛け合いの書き方:**

- **中盤で予想を裏切る展開を1つ以上入れる。** 大輔が置いた使い道・主張を沙織が資料で崩す（kl042: 総合1位でも画面操作は4.83%。kl031: 「体にいい方」は
  3.8点）、逆にツッコミが疑った点が数字で覆る（kl031: 730万回で1回は「くじ引き」ではなく学習の証拠、とツッコミが
  認める）、意外な結果（kl032: 一番低い39cmの台が一番成功）など
- **相手の発言に反応させる。** 「AがXを説明 → BがYを説明」のような説明の分担にしない。相づち・聞き返し・言い直し・
  譲歩・反論でつなぐ。大輔の主張が崩されたら、使い道の範囲を狭めてその論点の中で着地させる（v3。kl042 までの
  「言い直した夢をもう一度描く」は、12話中9話で同じ型になったためやめた）
- **二人の口調を書き分ける。** 大輔は「〜でしょ」「〜なんだ」「次は、どこで使える？」、熱が入ると1行が長くなる。
  ツッコミは短く、「で、」「ちなみに」「〜ね」、数字で返す。どちらも敬語は使わない（同期の会話）
- **ツッコミの口癖「何人で試したの？」は、その回の中身に合わせて言い換えてよい**（「何人で嗅いだの？」「何回試したの？」）
- **分からないことは分からないと言わせる。** 論文が説明していないことは「論文には書いてない。そこは分からない、で止めておこう」
- **1行は耳で聞いて分かる長さに。** 数字が3つ以上続く行は分ける。teaser は30字以内
- **常套句の禁止（`kl_dialogue.PHRASE_LIMITS`）:** 「頭ではわかって」「胸の奥」「ふっと」「ささやか」は使わない。
  「それでも、」は2回まで、「研究段階」は1回まで、「かもしれません」は2回まで（旧形式で30話に繰り返し出た言い回し）
- **「小さな幸せ」固定のオチは廃止した。** 結末は判定に従う。「まだ眉唾」なら希望で無理に締めない
- **研究者個人の名前は台詞に入れない。** 大学・機関名は言う。「査読」「プレプリント」の語は台詞で使わない
  （「まだほかの専門家の審査を受ける前の論文」のように言い換える。概要欄では明記する）
- **健康の話題は研究結果の紹介にとどめる。** 視聴者への助言・指示（「〜しましょう」等）を書かない。二人に
  医師・専門家を名乗らせない（ツッコミ担当は「臨床研究・統計に強い」人物設定だが、台詞で専門家として助言はしない）。
  研究段階の結果を確立した治療のように語らない。`kl_fact_check.py` がこの3点を確認する
- 数字はTTSが読める表記にする（「2216件」「7点満点で3.8」など算用数字でよい）。字幕だけ別の表記にしたいときは
  その行に `display` を書く

**判定（チャンネルの看板）:**

- トップレベルの `verdict: {"dreamer": key, "skeptic": key}`。key は `soon`（もうすぐ来る）／`decade`（3年はかかる）／
  `pending`（根拠待ち、2026-10-18追加）／`dubious`（まだ眉唾）。ラベルの文言と色は `cast.json` の `verdicts`。使い分け:
  - `soon`: もう使える形で出ている、または1年ほどで出そう
  - `decade`: お題の主張そのものが3年以内に来そうで、物理的・臨床的な壁があるとき（AI・ソフトウェアの運用上の制限には使わない、2026-10-06）
  - `pending`: 否定する資料は無いが、支える資料もまだ無い。3年を超える主張（遠い先の予測）はこれ
  - `dubious`: 資料が逆の向きを示している、主張が資料の範囲を大きく超えている、数字が誇張されている、のどれか
- **札は、お題の主張（話者が言った時期・範囲のまま）に対して付ける。部分的な問いにすり替えない**（2026-10-18。kl046 の初稿で、
  マスク氏の「2036年にお金は意味を失う」に対し、大輔が「食べ物や電気が安くなり始めるまで3年」という別の問いで「3年はかかる」を付けていた）
- **`pending` を付けたら、「何が確かめられたら札が変わるか」を台詞で必ず一言言う**（上げる条件。下げる条件もあればなお良い）
- **年数の見通しは3年先までにする（2026-10-05、なるさんの指示）。** AIの発達で研究の進みが速く、10年先は予測できない。「10年」「十年後」を台詞に書かない。3年を超えそうなら、期間を言い切らず「そこまでは分からない」と言い、**3年を超える主張は `pending`（資料が逆を示すなら `dubious`）**にする（2026-10-18改訂。旧: 「判定は `dubious` か、3年先までの話に絞る」）。
- 「根拠待ち」が逃げの札にならないよう、直近5話で判定（二人分）の半分を超えていないかをSTEP5で見る
- 判定は毎回変わること。**二人の判定が割れる回もあってよい**（kl031は割れ、kl032は一致）。直近の回と同じ判定が
  続いていないかをSTEP5で見る
- `verdict` シーンの `verdict_from_line`（1始まり）の行から、画面に判定ラベルが出る（割れたら二人分）。
  両方の判定を言い終えた行にすると、ラベルが台詞を先取りしない
- 判定の根拠は論文に書いてあることから言う。大輔の判定が「別の問い」への答えになっていたら、ツッコミが
  「それは〜の判定でしょ」と指摘してよい（kl031）

**締めの固定（`kl_dialogue.CLOSING_CTA`）:** `closing` の最後の2行はこのとおりにする（2026-08-31に確定した
固定文を二人の声に分けたもの）。その前に、その回ならではの一言を1〜2往復置く。

> 大輔「次はどんな研究が、誰かの幸せな未来を運んでくるのか。」（2026-10-17、構成 v3 でも変えない）
> ツッコミ「それが本物かどうか、また一緒に確かめましょう。論文は概要欄に載せています。チャンネル登録して、待っていてください。」

**台詞のフィールド（`scenes[].lines[]`）:**

| フィールド | 内容 |
|---|---|
| `speaker` | `dreamer` / `skeptic` |
| `text` | 台詞（TTSが読む） |
| `expression` | 話している人の表情（`cast.json` の expressions のキー。dreamer: neutral/excited/surprised/thinking/deflated/convinced、skeptic: neutral/doubt/surprised/thinking/amused/convinced） |
| `react` | 任意。聞いている側の表情（省略時 neutral） |
| `tone` | 任意。その行だけの演技指導（英語。例 "sheepish, slower"）。`cast.json` の style に足される |
| `pause` | 任意。この行の前の間（秒）。省略時は話者交代0.28秒・同じ話者0.22秒。「……」で間を取りたい行は0.4〜0.6 |
| `tag` | 任意。`question`/`weakness`/`barrier`/`prediction`/`turn`/`vs_prediction`、v3 は `use_case`/`takeaway`（`life_scene` は kl042 まで） |
| `display` | 任意。字幕だけ別表記にしたいとき |

`t0`・`dur`（シーン音声内の位置）・`cards`（字幕）・シーンの `lines_hash` はスクリプトが書く。手で書かない。

**画像プロンプト（`image_prompt`）:**

- **二人（大輔・沙織）は画像に描かない。** 二人は固定の立ち絵（`assets/cast/`）を `kl_video_gen.py` が合成する。
  画像は「話題の中身」を見せる背景・挿絵にする（研究室、試食会場、未来の暮らしの場面、データ）
- `kl_image_gen.py` が掛け合い形式の構図の制約（左下・右下に立ち絵、下部に字幕帯が乗るので、主題を上〜中央に置く）を
  自動で付ける。プロンプトに重ねて書かなくてよい
- `paper` シーンは研究室の実験風景。研究者は分野を問わず白衣、論文の実施国に応じた人種で描く（旧形式と同じ）
- （v2 では使わない。kl040 までの記録）`dream` シーンの人物（未来の暮らしの当事者）は、匿名の生活者として容姿を固定の一文（髪型・髪色・年齢・服）で書き、
  同じ回の別シーン（`setup` 等）に同じ人が出るなら文言をそのまま使い回す。**v2（kl041〜）では上の「画面（v2）」に従い、
  年齢・容姿を決めた人物を描かない。v3（kl043〜）では dream 自体が任意・1つまで。** **`dream` シーンに「幸せな未来を夢想中」の
  バッジ（`badge_text`）は付けない**（2026-10-05、なるさんの指示。あのバッジは「不特定の主人公が夢想する」旧形式で
  現実と想像を分けるためのもので、二人の掛け合いでは夢語りが「想像してみてよ」と言って始めるので不要）
- 研究の被験者・参加者は匿名の人物として描き、`dream` の人物と同じ容姿にしない
- ロボットは同じ回の中で同一デザインの説明文を使い回す。顔は人間の顔にせず機械的に（旧形式と同じ）
- **実在の製品・機体（ニュースで扱う製品など）を描くときは、想像で描かない（2026-10-05、kl032で発覚）。** kl032で
  Flourish 1を「白くて滑らかなヒューマノイド風」と想像で描いたところ、実物は緑のきのこ帽子・円柱の胴体・簡易なつかみ手の
  素朴なロボットで、まったく別物だったとなるさんに指摘された。ニュースは実物と違う絵だと誤解を招く。手順:
  (1) 台本を書く前に、公式サイト・プレスリリース・報道の写真（ブラウザで見る。写真自体は許諾なく動画に使わない）で外観を確認する。
  Tau Roboticsのように公式サイトに写真があれば見る (2) 外観の特徴（形・色・部品・大きさ・車輪/脚の数）を言葉にして、
  その回のimage_promptに毎回貼る。写真をそのまま参照画像として渡さない (3) エピソードJSONに `depicts_real_product: true`、
  該当シーンに `shows_product: true` と `badge_text: "イメージ図（実物と異なる場合があります）"`（Shortsのカットにも）を付け、
  概要欄にも「イメージ図」の注記を入れる（`kl_dialogue.py check` が確認する） (4) 外観が確認できない製品は、特定の
  製品に見えない汎用的な描き方にし、同じ注記を付ける
- `check` シーンはチャート調。数字・ラベルは論文本文に実際にある値だけを、`image_prompt` に一字一句書く
  （捏造禁止、`docs/production_tech.md`「画像スタイル」）。軸は0から始めて比率を誇張しない
- 文字は入れない（`check` のラベル以外）。時間帯は視覚的に明示する
- teaser のカットが本編の場面と同じなら `reuse_scene_id`、固定背景なら `image_asset`

**タイトル・サムネイル・フック:**

- `youtube_title`: `entry_question` を土台に、視聴者の問い・意外性を主語にする。30〜40字。チャンネル名・【】を付けない
  （旧形式と同じ）
- `thumbnail_prompt`: 背景だけを描く（二人・文字は合成する）。主題を中央の帯に置く。`thumbnail_headline`（1〜2行、
  改行は `\n`）、`thumbnail_exprs`（例 `{"dreamer": "excited", "skeptic": "doubt"}`）。`kl_image_gen.py` が
  見出し＋二人の立ち絵＋判定ラベルを合成する（`kl_dialogue.composite_thumbnail_dialogue`）
- `hook_lines`（2行、各10〜16字）: Shortsの1カット目に大きく出る

**Shorts（`shorts[0].scenes`、5〜6カット）:** 「問い → 大輔の期待・使い道の一言 → 沙織の資料での一言で切る → 判定は本編で」。
各カットは `narrator`（dreamer/skeptic）・`narration`・`expression`（任意で `react`・`tone`）と、本編の場面の
`scene_id`（画像を9:16に再構成する）を持つ。1カット目は15字以内、最後のカットに「本編」を含める。
最後のカットには `kl_video_gen.py` が「判定は本編で」のラベルと「↓ 続きは本編で」を重ねる。
本編の台詞と一字一句同じカットは本編の音声を流用する。

**JSONのトップレベル:** `episode_id` / `format: "dialogue"` / `template` / `episode_title` / `youtube_title` /
`entry_question` / `verdict` / `hook_lines` / `thumbnail_prompt` / `thumbnail_headline` / `thumbnail_exprs` /
`youtube_tags` / `references[]`（`institution` を含める。ファクトチェックが所属機関の表記を照合する） /
`youtube_description`（判定、研究の要約、査読前の開示、参考文献。**「二人は架空のキャラクターで声はAI」の注記は書かない**
（2026-10-05、なるさんの判断。必須ではなく、公開済みの動画とも揃わないため。合成コンテンツの申告はアップロード時の設定で
入っている）。実在の製品を絵に描く回は「イメージ図」の注記を入れる） / `scenes[]` / `shorts[]`。

## STEP 4 — 台本ファクトチェック

```bash
python3 kl_fact_check.py --episode kl{NNN}
```

`ok` 以外が出たら、論文本文（WebFetch）で確認して台詞を直し、`kl_dialogue.py check` → 再チェック。

**資料カード（v2 の `source_card`）も資料ごとの照合に入る（2026-10-16〜）。** `kl_fact_check.py` がカードの引用・要約を
`reference_index` の資料に振り分け、`quote_type: "原文"` の引用が一字一句同じか（前後を切った連続の抜き出しは一致扱い）を
`card_quote_exact` で返す（不一致なら caution）。Gemini の照合は図の種類などで誤ることがある（kl041 で棒グラフを
「レーダーチャート」と誤指摘）ので、caution は一次資料を開いて確かめてから直す。原文の引用は、公開前に一次資料の
HTML を取得して文字列で一致を確かめると確実。
**台本を書いた側が論文を読み違えていることがある。** kl031では「香りは食べものに乗せていない」と書いたが、実際は植物性
ソーセージで試食まで行っていた（ファクトチェックで発覚）。指摘は台本側の思い込みを疑ってから直す。

## STEP 5 — 台本の面白さ・品質レビュー（Opusサブエージェント、2026-10-04改訂）

STEP4の後、`Agent`（`model: "opus"`、`subagent_type: "general-purpose"`）に台本のレビューと直接修正を任せる
（結果を待ってからSTEP6へ）。台本を書いたモデルとは別の目で読ませる。プロンプトには次を含める:
エピソードJSONと `cast.json`・`kl_dialogue.py` のパス、番組を掛け合い形式に変えた理由（STEP2冒頭）、下の観点、
守るべきルール（数値・事実を変えない／足さない、名前を台詞に入れない、締めの固定文を変えない、常套句の上限、
teaser30字・Shorts1カット目15字。尺は制約にしない＝伝わることが最優先）、修正後に `kl_dialogue.py check` を通すこと、報告の形式
（総評・修正の要約・修正しなかった懸念・GO/NO-GO）。

**観点（面白さ）:**
1. 冒頭の問いに対して、中盤で予想を裏切る展開が1つ以上あるか
2. ツッコミが具体的か（数字・条件を伴っているか）。形だけの反論になっていないか
3. 二人の口調・語彙が明確に区別できるか
4. 判定が論文の内容から妥当か。直近の回と同じ判定・同じテンプレート・同じ締めが続いていないか
   （`topics_queue.json` と直近の `episodes/kl*.json` の `verdict`・`template` を渡す）
   - 札がお題の主張（話者が言った時期・範囲のまま）に対して付いているか。部分的な問いにすり替えていないか（2026-10-18）
   - `pending`（根拠待ち）を付けた人が、「何が確かめられたら札が変わるか」を台詞で言っているか。直近5話で根拠待ちが判定の半分を超えていないか
5. 掛け合いが一方的な説明の分担になっていないか（相手の発言に反応しているか）
6. （v2）論点の見出しが視聴者の問いになっているか。各論点で「どちらが譲ったか」が分かるか。最初の予想と判定の
   つながり（`vs_prediction`）が、こじつけになっていないか。夢が使い捨ての生活者の物語に戻っていないか
7. （v3）`use_case` が視聴者の置き換えられる具体的な作業で、すぐ後の資料に本当に当てているか（資料と無関係な夢になっていないか）。
   大輔が正しかった論点（沙織が譲る `turn`）があるか（check の ⚠ を見る）。`takeaway` が「誰が・何に・どんな条件で／いつ」まで
   具体的か、判定ラベルと食い違っていないか、健康の話題で助言になっていないか。dream を置いたなら、絵にする価値がある回か

**観点（品質、旧STEP5から継続）:** 不自然な日本語、特定の属性を見下していないか、健康の助言・専門家の名乗り・言い過ぎ。

**観点（耳で聞いて分かるか。2026-10-19に独立させた）:** `kl_prompts/script_writer_rules.md` の規則 (a)〜(l) を、このレビューのプロンプトにも
全文入れる。`kl_dialogue.py check` の「読みやすさの手がかり」（⚠）を一つずつ見て、直すか、直さない理由を書く。
**ただし、このレビュー役も資料を見ているので、分かりにくさを見落とす（kl046で実際に起きた）。「伝わるか」の最終判定は、
STEP5.5 の初見レビュー（資料を見ていない別のOpus）で行う。** STEP5 は面白さ・規則・事実の確認が主で、STEP5.5 を省略する理由にはならない。

レビューが台詞を直したら、**数値や事実に触れる修正があった場合だけ** `kl_fact_check.py` を再実行する。
レビューの「事実の確認が要る」という懸念は、メイン側で論文本文を確認して処理する（kl031では「キノコと牛肉を
混ぜたバーガーで肉がどれだけ減ったか」が本文に無いと分かり、夢語りの言い直しと判定を書き換えた）。

制作確認書（`kl_confirmation_doc.py`）は旧形式向けのため、掛け合い形式では省略してよい（台本の確認は
`kl_dialogue.py check` の出力とこのレビューで行う）。

## STEP 5.5 — 初見レビュー（必須ゲート、2026-10-19〜）

**ファクトチェック（STEP4）・面白さのレビュー（STEP5）・機械チェックの後、画像・音声を作る前に必ず通す。合格するまで STEP6 に
進まない。**

**TTS（`kl_tts_gen.py`）と動画生成（`kl_video_gen.py`、本編・Shorts のどの経路でも）は、初見レビューが「済」でないと終了コード2で止まる**
（2026-10-19〜、なるさんの指示「しばらくはそうしてほしい」。対象は `"structure": "rounds_v3"`・`"rounds_v4"` で kl046 以降。判定は `check` の表示と同じ
`kl_dialogue.beginner_review_state`）。`--skip-beginner-review`（または `KL_SKIP_BEGINNER_REVIEW=1`）で飛ばせるが、**制作者の了承なしに使わない。** 資料を見ていない別のOpusに、台詞と画面の文字だけを読ませ、初めて聞く人がどこで詰まるかを洗い出す。

**なぜ必須か（2026-10-19、kl046）:** kl046 は、Opusが書き、別のOpusがレビューし、`check` とファクトチェックを通した台本でも、制作者から
「意味がわからない」「主語がない」「モデルて何？」「たとえがわからない」が1つずつ10回近く続いた。書き手もレビュー役も資料を読んで
いて、分からない立場で読む工程が無かったため。資料を見ていないOpusに読ませた初見レビューは、1回で35件（うち致命的3件）を挙げ、
制作者が指摘していた種類の問題をまとめて拾えた。

**手順（メインがこのとおりに行う）:**
1. 台詞だけのテキストを作る（リポジトリの外、scratchpad などに置く）:
   ```bash
   python3 kl_dialogue.py plain --episode kl{NNN} --out {scratchpad}/kl{NNN}_plain_r1.txt
   ```
   台詞（字幕の表記）・画面の資料カード・図の文字・論点の見出し・判定ラベルだけが入る。概要欄・資料・英文の作画指示は入らない。
2. `kl_prompts/beginner_review_prompt.md` の「依頼文」の `{PLAIN_PATH}` と `{OUT_PATH}`（例 `{scratchpad}/kl{NNN}_beginner_review_r1.md`）を
   置き換えて、`Agent`（`subagent_type: "general-purpose"`、`model: "opus"`、`run_in_background: false`）に渡す。
   **プロンプトには、plain テキストのパス以外の情報（JSON・概要欄・資料・経緯・前のレビュー）を書かない。** 書くと「分かってしまう」。
3. 結果を台本の書き手（Opusサブエージェント。STEP2と同じ形で新しく起こしてよい）に渡して直させる。渡すものは、レビュー結果の
   パス、`kl_prompts/script_writer_rules.md`、エピソードJSON、資料。指示は次のとおり。
   - 【致命的】【直す】は全部反映する
   - 【できれば】は、伝わりが良くなるなら反映する
   - 反映しない項目は理由を書く
   - **レビューの直し案には、資料の範囲を超える言い方が混ざる**（為替の換算、資料に無い理由づけ、発言の範囲を超える説明）。
     原典で確かめてから台詞にする
   - 直した後、台本全体を初見の目で通して読み、同種の問題を探して直す
   - 数値・事実に触れたら `kl_fact_check.py` を再実行する
   - `kl_dialogue.py check` を❌ゼロで通す
4. 直した台本で 1〜2 をやり直す（**毎回新しいサブエージェントで、前のレビュー結果は渡さない**）。
5. **合格基準:** 【致命的】ゼロ、【直す】がすべて反映済み（反映しないものは理由つき）、直した全体をもう一度通して【致命的】が出ない。
   **目安は2周。** 2周目で【致命的】が残っても、直せる種類なら直して3周目を通し、事後報告する（2026-10-24〜）。直せない
   （資料が足りない・お題の組み直しが要る）ときだけ、制作者に状況を報告して判断を仰ぐ。周回のたびに説明が足されて台本が膨らむので、
   3周目の前に繰り返しと数字を削る（kl048: 4,900字→6,400字に膨らみ、削ってから3周目を通した）。
6. 合格したら記録する:
   ```bash
   python3 kl_dialogue.py review-pass --episode kl{NNN} --rounds {周回数} --report {最後のレビュー結果のパス}
   ```
   記録には台詞のハッシュが入る。後で台詞を1文字でも変えると、`check` が「初見レビュー: 無効（台詞が変わった）」と出す。
   **制作者の指摘で台詞を直したときも、制作者に見せる前にこの STEP をやり直す**（下の「制作者に台本を見せる形」）。

## STEP 6.5 — dataタイプ画像の可読性レビュー（Opusサブエージェントに委任、2026-09-01追加）

**掛け合い形式では `type: "check"` のシーンが対象（旧形式の `data` と同じ扱い）。** 加えて、左右の端に立ち絵が
重なるので、図の端のラベルが隠れないかも見る（`kl_image_gen.py` は図を中央70%に収める指示を自動で付けている）。
v2 の資料カード（`source_card`）も対象に含める。見るのは、台詞が読み上げている箇所と強調（`highlight`）が合っているか、
文字が小さすぎないか（1行26字が目安）、原文と要約の区別（カードの右下）が正しいか。カードは `source_card` を直して
`kl_dialogue.py cards` を再実行すれば作り直せる（画像生成は不要）。

STEP6の自動画像QA（`kl_image_gen.py`内のGemini Vision）は「歪み・文字混入・
スタイル逸脱・シーン内容との齟齬」等の機械的な観点しか見ておらず、**「人間が
見て図の意味が伝わるか」という可読性の観点は一度もチェックされていない。**
kl012で実際に、(a) 単純な2本比較のはずが片方が誤って2本の棒に分かれていた
（`人だけのチーム`側）、(b) 散布図に軸の説明が一切なく何を表しているか
分からない、という2件がSTEP11の人間確認で初めて発覚した。STAGE2.5がナレー
ションの文章のみを対象にした人間視点レビュー（Opus）であるのと同じ考え方で、
画像についても生成直後に同種のレビューを挟む。

`episodes/kl{NNN}.json`の`scenes`のうち`type: "data"`のシーン、および
`shorts[].scenes[]`のうち`style: "chart"`のカットを対象に、`Agent`ツールで
`model: "opus"`のサブエージェントに委任する（`run_in_background: false`、
結果を待ってからSTEP7へ進む）。対象画像ファイルのパス（
`~/Desktop/kagaku-life/images/`配下）と、対応するシーンの`narration`・
`image_prompt`をAgentプロンプトに含め、Read toolで画像を直接見て以下を
判定させる。

**あわせて以下もAgentプロンプトに含める（2026-09-29追加）:** サブエージェントは
会話履歴を持たず、対象シーン単体の情報だけでは「このグラフが話の流れの中で
何を示すべきか」「どの数値なら使ってよいか」を判断できないため。
- 対象シーンの**直前・直後のシーン**の`scene_id`・`type`・`narration`
  （グラフが前後の文脈で何を受けて何につなぐのかを判断させるため）と、
  `reference_index`が指す`references[]`の論文タイトル・URL
- **捏造禁止の方針**: `docs/production_tech.md`「画像スタイル（2026-08-21改訂）」節の
  data/chartに関する記述（「数字は捏造せず、論文本文に実際に記載されている
  数値のみを使う」「小さい変化量をそのままバーの高さにしない」等）の本文、
  または`$HOME/kagaku-life/docs/production_tech.md`のパスと節名を渡して読ませる。
  観点2の「軸ラベルを捏造しない」もこの方針に従う

**チェック観点:**
1. **比較対象の数・構成がナレーションと一致しているか**: 「2つを比べる」と
   ナレーションが述べているのに、画像上は一方が複数要素に分かれている等の
   ズレがないか（kl012 S12の実例）。
2. **軸・凡例・ラベルなしで意味が伝わるか**: 散布図・座標系を使った図で、
   何を近い/遠いと表現しているのかが一目で分かるか。分からない場合は、
   軸ラベルを捏造するのではなく、図の意味を説明する短いタイトル・キャプ
   ションを追加する方針で直す（kl012 S13の実例、CLAUDE.mdの「捏造禁止」
   方針と整合）。
3. **色・高さ・大きさの視覚的対応が、ナレーションが示す大小関係と矛盾して
   いないか**: 数値が大きい方が小さく描かれている等の逆転がないか。

**問題が見つかった場合は、ユーザー確認なしに`image_prompt`を直接修正した
うえで、`kl_image_gen.py --episode kl{NNN} --scenes {scene_id}`（Shortsは
`--shorts-scenes {番号}`）を実行して再生成させる。** 再生成後の画像も
同じ観点で確認し、解決するまで（目安2回まで）繰り返す。オーケストレーターは
完了報告（修正したシーンとその内容の要約）のみ受け取る。

`data`タイプ・`style: "chart"`のシーンが存在しないエピソード（企画上
グラフを使わない回）ではこのSTEPは自動的にスキップしてよい。

## STEP 6.6 — 自動QAのall_okを鵜呑みにしない（2026-09-10追加・SC横展開）

STEP6の自動画像QA（`kl_image_gen.py`内、`QA_MODEL = "gemini-flash-latest"`）は、
samurai-chroniclesの同型パイプライン（`sc_image_gen.py`、全く同じモデル・同じ

偽陽性（正しい画像を誤って"NG"と判定）の両方が実際に発生した実績がある**
（ep098竹中半兵衛で確認）。KLはコードを移植した同一のQA機構を使っているため、
同じ限界を抱えている可能性が高い。

STEP6.5は`data`/`chart`シーンの「可読性」という別の観点のチェックであり、
**それ以外のnarrative系シーンについては、STEP6完了後この時点までClaudeが
一度も実際の画像を見ていない**（`all_ok: true`という文字列を信じているだけ）。
STEP11でユーザーに確認ページを見せる前に、主要シーン（サムネイル・Shorts
ハイライト・その他目立つ構図のシーン）を`Read`ツールで一通り目視し、
`image_prompt`の意図と明らかに食い違う画像（人物の人数・年代・表情、
時代考証相当の逸脱等）がないか確認する。問題が見つかった場合は、
STEP6.5と同じ要領でユーザー確認なしに`image_prompt`を修正し
`kl_image_gen.py --episode kl{NNN} --scenes {scene_id}`で再生成する。
**同じシーンを2実行しても直らない場合は、それ以上Sonnetメインで再調整を続けず、
ユーザーに確認せずOpusサブエージェントに引き継ぐ**（2026-09-29〜。`kl_image_gen.py`は
1実行の中で自動リトライするため、1実行＝1試行と数える。引き継ぎには、シーンの
`narration`・元の`image_prompt`と修正後の`image_prompt`・QAの指摘・画像のパスを書く。
CLAUDE.md「モデルの使い分けとOpusへのエスカレーション」参照）。

全シーンを1枚ずつ精査する必要はない（KLにはSCの`character_ref`のような
**エピソードを跨いだ**固定キャラクターの参照画像機構は存在しないため、
SCほど網羅的な確認は必須ではない）が、`all_ok: true`だけで無条件にSTEP11へ
進むことはしない。**ただし「エピソードを跨いだ仕組みが無い」ことは
「1エピソード内での主人公の容姿一貫性を確認しなくてよい」ことを意味しない
——この観点はSTEP6.7で別途扱う。**

## STEP 6.7 — 主人公・家族の容姿一貫性チェック（2026-09-11追加）

**掛け合い形式（2026-10-04〜）では「主人公」はいない。** 二人（大輔・沙織）は固定の立ち絵なので確認不要。
代わりに、同じ回で複数シーンに出る人物（`setup` と `dream` に出る匿名の生活者とその家族）と、ロボットのデザインの
一貫性をこの手順で確認する。`paper`/`check` の被験者・研究者は、`dream` の人物と別人に見えること。
以下の記述の「主人公」は、掛け合い形式では「複数シーンに出る匿名の生活者」と読み替える。
**v2（`structure: rounds_v2`、kl041〜）では、年齢・容姿を決めた人物を描かないので、人物の一貫性チェックは原則不要。**
見るのは (1) 同じ回で複数シーンに出るロボット・製品・場所のデザインの一貫性、(2) `dream` の手元・後ろ姿が、特定の
年齢・性別の「主人公」に見えるほど描き込まれていないか、(3) 実在の製品の外観（`depicts_real_product`）。
**v3・v4（`structure: rounds_v3`／`rounds_v4`、kl043〜）も同じ。** dream が無い回は (2) は不要で、(1)(3) と、使い道の場面の挿絵に人物が
描き込まれすぎていないかだけを見る。

kl007制作（2026-08-29）で、主人公の髪色が黒髪のシーンと白髪（グレー）の
シーンで混在するという事故が発生した。原因は`image_prompt`に髪色を明記
していなかったため、Gemini画像生成がシーンごとに「単体では"あり得る"が
他シーンとは矛盾する」外見をそのつど選んでしまったこと。同じ回で、ある
シーンが「彼女の家族」とだけ記述していたために、他シーンで明示された
夫（50代）・娘（20代）と矛盾する若い男性＋白髪の高齢女性が生成された
事故も同時に発覚した。ユーザーが目視で気づいた（「主人公の髪型が、黒髪
だったり白髪だったりバラバラ」）まで、STEP6の自動QAはこの種の不整合を
一度も検出できていない。

STEP6.5/6.6のチェックは「1枚の画像がそのシーン単体のimage_prompt・
ナレーションと整合しているか」を見るものであり、**主人公本人の髪型・
髪色・年齢感・体格が、他のシーンに登場する同一人物と一致しているか**
という横断的な同一性は対象外（各シーンが独立して判定されるため、単体で
は自然な外見でも他シーンと矛盾する場合に検出できない）。

**流れ:**
1. 主人公が登場する全シーン（`citation`/`finding`/`data`を除く。CLAUDE.md
   のルール上これらのシーンには主人公が登場しないため対象外）の画像を
   `Read`ツールで並べて確認し、髪型・髪色・年齢感・体格が同一人物として
   一貫しているか確認する。
2. 主人公以外に繰り返し登場する人物（家族・同僚等）がいる場合、同様に
   外見の一貫性を確認する。
3. `image_prompt`側で外見記述が曖昧な箇所（例:「彼女の家族」とだけ書かれ、
   年齢・性別・人数が明記されていない）がないか、JSONのテキストレベルでも
   確認する。
4. 不一致が見つかった場合、該当シーンの`image_prompt`に固定の外見
   descriptor（髪色・髪型・年齢・体格を明記した一文）を追記し、
   `kl_image_gen.py --episode kl{NNN} --scenes {scene_id}`で再生成する。
   以後、そのエピソードの他シーンでも同じdescriptorの文言を使い回す。

### 横断チェックはOpusサブエージェントに委任する（2026-09-29〜）

上記1〜2の画像の横断確認は、以前は「STEP6.6と同じくメインが自分で`Read`して
行えばよく、サブエージェントは不要」としていたが、これを改める。Sonnetメインの
目視では、シーン間の食い違いを見落とす構造的な弱点がある（lamp-whisper LW088で、

すべてユーザー指摘で発覚した。kl007・kl016もユーザー指摘まで検出されていない）。
そこで、上記3（JSONのテキスト確認）をメインが済ませたあと、画像の横断確認は
Agent ツール（`model: "opus"`、`subagent_type: "general-purpose"`）に委任する。

**サブエージェントは会話の経緯を持たないため、呼び出し前にメイン会話で
「シーン設定表」を作って渡す:**

```
S07: type=finding / narration=「…」 / 登場人物=匿名の被験者（主人公ではない）
S14: type=impact / narration=「…」 / 時代・場面=未来・自宅 / 登場人物=主人公・夫・統合ロボット
…
一致しているべきもの: 主人公の容姿（descriptorの文言をそのまま書く）、家族の人数・年齢・性別、

違っているべきもの: citation/finding/dataの被験者 ⇔ 主人公（kl016の事故）
既に決まっていること: 吹き出しは最初のimpactだけ（2枚目以降は badge_text）、dataシーンは画風が違ってよい（対象外）
```

```
    kagaku-life kl{NNN} の静止画について、同じ人物・同じ物がシーン間で一貫しているか、
```

```bash
python3 kl_image_gen.py --episode kl{NNN} --scenes 14 --reference-scene 9
```
`--reference-scene`は1回の実行につき1枚で、その実行の全シーンに同じ画像が渡るため、
**不一致のシーンは1シーンずつ別々に実行する**。用途は主人公・家族・統合ロボットの同一性に限り、
構図・背景のコピーには使わない（kl004の判断どおり）。

**再生成の上限:** Sonnetメインでの再生成は同じシーンにつき2実行まで（`kl_image_gen.py`は
1実行の中で自動リトライするため、1実行＝1試行と数える）。2実行で直らなければ、
ユーザーに確認せず、そのシーンの修正をOpusサブエージェントに引き継ぐ（CLAUDE.md
「モデルの使い分けとOpusへのエスカレーション」参照）。Opusでも直らない場合に限り、
STEP11の確認でユーザーに諮る。

**要相談は新しい確認ステップにせず、STEP11のユーザー確認に選択肢付きで含める。**

## STEP 7 — zoom_anchor判定・カメラワーク自動決定（実行タイミングに注意）

**このSTEPはSCと完全に同じ仕様で、全シーンの`ken_burns`を判定結果で
上書きする（2026-08-25確定）。** STEP2でシーンJSONに書いた`ken_burns`

`character_ref`の有無だけで機械的に決めるのと同じ）: 1人構図→`zoom_in`、
2人構図→`pan_zoom_out`、0人/3人以上→`zoom_out`。結果として`static`/

**このSTEPの実行は、STEP11で画像・ナレーション・BGMのユーザー確認がすべて
OKになった「後」まで待つこと（2026-08-25改訂）。** zoom_anchorは静止画の
主被写体位置を判定してKen Burnsの焦点をJSONに書き込む処理のため、レビュー
段階で画像が差し替えになった場合、レビュー前に実行すると無駄になる

実行コマンドは以下（STEP11「OKが得られたら」の直後、`kl_finalize.py`より前に


## STEP 8 — ナレーション音声生成

**TTS・動画生成は、初見レビュー（STEP5.5）が「済」でないと止まる**（rounds_v3・rounds_v4 の kl046 以降。`--skip-beginner-review` で飛ばせるが、
制作者の了承なしに使わない）。始める前に `kl_dialogue.py check` で「済」を確かめる（「無効」なら台詞が合格の後に変わっている。
制作者の指摘で台詞を直したら、STEP5.5 をやり直して `review-pass` で記録し直す）。

```bash
python3 kl_tts_gen.py --episode kl{NNN}
```

**掛け合い形式:** 台詞を1行ずつ、話者の声（`cast.json`）で生成し（`narration/S{NN}_L{KK}.wav`）、話者交代の間を入れて
音量をそろえ、シーン音声 `S{NN}.wav` に連結する。各行の位置（`lines[].t0`/`dur`）とシーンの `lines_hash` を
エピソードJSONに書き込む。台詞を直した行だけが作り直される（`S{NN}_L{KK}.txt` に生成時の台詞と演技指導を記録）。
**台詞を直したら必ずそのシーンの音声を作り直す**（`kl_video_gen.py` は `lines_hash` が合わないと止まる）。

**読み照合QA（2026-10-11追加、`kl_reading_qa.py`）:** 既存の Gemini QA（台本どおりか）を通った各行を、言語モデルを持たない
音素認識（`prj-beatrice/japanese-hubert-base-phoneme-ctc-v4`、初回に約380MBを `~/.cache/kl_reading_qa_hf` へ取得）で
「聞こえたとおりの音」にし、台本の期待する読み（Gemini Pro がテキストから文脈込みで決めたカタカナ。台詞のハッシュで
`~/.cache/kl_reading_qa/readings.json` にキャッシュ）と行内の局所的な差ごとに照合する。数字（年齢・人数・割合など）の
範囲にかかる差は低いしきい値で別枠に判定する。長音・「おう/おー」「いう/ゆう」・数字の促音便（イチテン/イッテン）は
ゆれとして無視する。**不一致の行だけ作り直し（最大3回）、残ったら一番ましな音声で続行**し、結果を
`narration/reading_qa.json` に行ごとに残して最後にまとめて表示する。表示された行は STEP 11 で必ず耳で確認し、
誤読なら台本の語を言い換える（作り直しで直らない誤読は、語の言い換えが確実）。`--no-reading-qa` で無効化。
既存の音声だけを照合するときは `python3 kl_reading_qa.py --episode kl{NNN} --narration-dir <S{NN}.wavのフォルダ>`
（音声もJSONも書き換えない）。**限界:** 長音の脱落（どうして→どして）は検出しない。非常に速い発話では認識が音を
落とすことがあり、大きな抜けだけの差は「不確か」として不一致にしない（読み飛ばしは Gemini QA が見る）。期待する読みは
LLM が決めるため、2通りに読める語で LLM が片方しか挙げないと誤検知になる。旧形式（独白）には未対応。

## STEP 9 — テロップ生成

```bash
python3 kl_telop_gen.py --episode kl{NNN} plan
```

**掛け合い形式:** 台詞1行ごとに字幕を作る。38字以下の行は1枚、長い行だけWhisperで行ごとの音声を解析して分ける
（`lines[].cards`）。字幕は画面下の帯に、話者の色で、最大2行で出る（描画は `kl_dialogue.render_layer`）。

生成後（STEP12）に複数箇所をフレーム抽出して確認する。

## STEP 10 — BGM選定

**方針（2026-10-06作り直し。正は `docs/bgm.md`「BGMパイプライン」→「掛け合い形式のBGM方針」）: BGMは二人の会話のテンポを支える
リズム。感情を語るのは台詞。** ジャンルや判定で曲調は変えない。禁止は epic/battle/war/horror、重い・攻撃的な曲、ボーカル、
泣きのストリングス、オルゴールや遅いソロピアノ。どこで切り替わるかは各シーンの `bgm_role`。

| 役割 | 主なシーン | 狙い | テンポ・楽器 |
|---|---|---|---|
| intro | teaser〜setup（v3。kl042 までは teaser〜dream） | ニュースの引き・「何それ？」のワクワク | 105〜125 BPM。シンセのアルペジオ／プラック＋軽いビート、明るい長調、頭2〜4小節で立ち上がる |
| main | tsukkomi・check | 考える・確かめるときの軽い緊張と遊び | 70〜100 BPM。lo-fi／ヒップホップのビート、ピチカート、薄いメロディ |
| outro | verdict・closing | 判定の決着感と軽い余韻 | 85〜100 BPM。intro と同系統を少し落ち着かせたもの（エレピ／ピアノ＋軽いビート） |

**長さ: 区間の長さ×0.7以上が目安。main は120秒以上**（掛け合い形式の main 区間は160〜200秒）。短い曲は `kl_video_gen.py` が
つなぎ目をクロスフェードでならしてループするが、つなぎ目を必ず聴いて確認する（`kl_bgm_final_check.py` がつなぎ目の前後を聴かせる）。

**ライブラリの使い方のルール:** 同じ曲は直近5話で1回まで。各話で3役割のうち最低1曲は新曲（main を優先）。
`used_in` が6話以上の曲は使わない（kl002-BGM-main・kl001-BGM-intro・kl001-BGM-outro・kl005-BGM-main・kl001-BGM-main・
kl002-BGM-outro）。旧形式向きの曲（ピアノのバラード・泣きのストリングス等、`era: legacy_monologue`）も使わない。

1. `bgm_library.json` を読み、上のルールを満たし、役割の狙いに合う既存曲を役割ごとに0〜1曲選ぶ（`era: dialogue`・`role_fit`・
   `bpm`・`has_beat` が記録されていればそれを使う。記録が無い旧い曲は、曲名・クレジットから判断できるものだけ）。
2. Freesoundから役割別に新規候補をダウンロードする（クエリは2語まで。例と避ける語は `docs/bgm.md` の表）:
   ```bash
   mkdir -p "$HOME/Desktop/kagaku-life/BGM"
   FREESOUND_API_KEY=$FREESOUND_API_KEY python3 kl_freesound_download.py \
     "<Q_intro>" "<Q_main>" "<Q_outro>" \
     "$HOME/Desktop/kagaku-life/BGM/" \
     --count 2 --round 0 --start-slot 1 \
     --library "$HOME/kagaku-life/bgm_library.json"
   ```
   - 3クエリを渡すと intro/main/outro の順に役割が付き、長さの下限（intro 90秒・main 120秒・outro 45秒）が決まる。1役割だけ
     探し直すときは `--role main` を付ける。下限を満たす候補が無いと30秒以上に緩めて探し直し「短い曲」と表示する
   - score 順の1位が良い曲とは限らないので `--count 2〜3` で複数取る。候補だけ見るなら `--list 10`
   - 0件・候補不足なら `--round 1` で次のページへ進むか、語を変える
3. 新規ダウンロード分を `kl_bgm_qa.py --dir` でボーカル混入チェックする（3回の多数決。1回でも「あり」なら不合格）。
   **判定が割れた曲**は、表示された時刻の前後5秒を聴いて確かめるか、`--model gemini-pro-latest` で取り直す
   （flash はソロピアノに「男性ボーカル」と答えるなど、判定が割れやすい。pro は実測で6曲×3回すべて一致した）。
   ライブラリ曲は再チェック不要
4. 役割ごとに、ライブラリ＋新規の候補から1曲に絞り、`~/Desktop/kagaku-life/BGM/` に `intro_*.mp3`／`main_*.mp3`／`outro_*.mp3`
   としてコピーする（役割ごとに1ファイルだけ置く。**元のファイル名（`BGM_candidate_NN_{FreesoundのID}_...`）を
   残すと、`kl_bgm_library.py --add` がクレジットと `source_id` を自動で拾える**。例: `main_BGM_candidate_02_668377_Lofi....mp3`）
5. `kl_bgm_final_check.py --episode kl{NNN}` で最終検証する（温度0で3回の中央値。最終行が「最終判定: 合格」か
   「最終判定: 要差し替え（main など）」）。狙いを伝えずに曲単体を聴き取り、その結果と、台詞＋BGMの簡易ミックス、ループの
   つなぎ目で、役割ごとに5項目を1〜5点で採点する。合格は役割ごとに全項目3点以上かつ平均3.5以上
6. 「要差し替え」の役割だけ差し替えて再検証する。**2回続けて不合格なら、Opus に引き継がず、その時点で不合格の役割をライブラリの曲に切り替える**（2026-10-26、なるさんの指示「BGMの選定に時間かかりすぎ。2回失敗したら、その時点でライブラリからの選曲に切り替える」。上の 1. のルールを満たすライブラリ曲から、役割の狙い・BPM・長さが合うものを選ぶ。このときは「最低1曲は新曲」を満たさなくてよい）。ライブラリ曲で最終検証を1回通し、合格なら本登録へ進む（kl049 は main の新曲が2回不合格 → kl037-BGM-main で合格）
7. 合格したら本登録する（新規曲は曲調も記録する）:
   - 新規曲の場合: `kl_bgm_library.py --add --episode kl{NNN} --role {role} --file {path} --stem {name}
     --bpm {BPM} --mood {bright,playful 等} --instruments {synth,lofi-beat 等} --has-beat yes --era dialogue`
     （Google Driveへ移動・`bgm_sources`に記録・ライブラリに新規追加。`duration` は自動で実測。ファイル名から
     FreesoundのIDが分からないときは `--source-id {ID}`）
   - 既存ライブラリ曲を採用した場合: `kl_bgm_library.py --use-library --episode kl{NNN} --role {role} --stem {library_id}`
     （ダウンロード・移動不要、`bgm_sources`に既存パスを記録・`used_in`を更新）
8. CC BYライセンス曲があれば `kl_inject_bgm_credit.py --episode kl{NNN} --credit-file {path}`
   でクレジットを概要欄に注入

## 制作者に台本を見せる形・指摘を受けたとき（2026-10-19〜、kl046の反省）

**見せる前のセルフチェック（メインが毎回、確認ページ・テキストを見せる前に行う。5問とも「はい」になるまで見せない）:**
1. キーワード（その回だけの言い方。例「爆発」「入り口」）を、初出の台詞で定義したか
2. 判定の札が何を指すか（何が・いつまでに）を、台詞で言っているか（例「この3年は、食べ物や電気が安くなり始めるまでの話」）
3. 誰の発言か・何の話か分からない文はないか（主語・指示語）
4. 前の台詞で出ていない発言・固有名詞を、知っている前提で引用していないか（例「マスクさんの『小切手を配る』」を初出で使う）
5. 数字は耳で追えるか（1行3つまで・丸めたか・大きさの感覚を添えたか）

あわせて、`kl_dialogue.py check` の「初見レビュー（STEP5.5）」が「済」であることを確かめる（「未実施」「無効」なら STEP5.5 へ戻る）。

**台本が完成したら（初見レビュー合格の後）、制作者の承認を待たずに Opus の判断で次の STEP へ進む**（2026-10-24、なるさんの指示
「次回から台本が完成したら、オーパスの判断で次のステップに進んでいい。確認ツールを見て、修正が必要ならその時に指示する」。
2026-10-22 の「確認ツールまで承認なしで進める」の再確認。kl048 では台本のテキストと直した行を2回見せて承認を待ったが、不要だった）。
制作者が台本を確かめるのは STEP11 の確認ページ。そこで修正の指示を受けて台詞を直したときだけ、変更後の台詞をテキストで見せる
（変えた行に印を付け、直した理由を1行ずつ添える）。初見レビュー（STEP5.5）・ファクトチェックは省略しない。
初見レビューで【致命的】が残ったときも、直せる種類（言葉の使い分けなど）なら直して周回を足し、その旨を事後報告する。

**制作者から分かりにくさの指摘を受けたら:**
- その1行だけでなく、**同じ種類の問題を台本全体から探して、まとめて直す**（kl046 では「モデルて何？」の後に、同じ種類の言葉
  ——資本・生産性・自動化・所得保障・ポイント——が残っていた。1つずつ直したため、制作者が1つずつ見つけることになった）
- 直すときに新しい用語・たとえ・言い回しを足したら、それ自体が初見で通じるかを確かめる（kl046 では「お金の入り口」「経済モデル」
  「機械」を足したことが、次の指摘の種になった）
- たとえ話・仕組みの指摘は、まず原典に戻って、台詞が仕組みを取り違えていないかを確かめる（kl046 の「人を手伝う機械」は取り違えだった）
- 直したら STEP5.5（初見レビュー）を通してから見せる

## STEP 12 — 動画生成

動画生成前に、実際のナレーション音声長の合計を測って報告する。**尺の長短だけを理由に台本を直したり、ユーザーに確認したりしない**
（最優先は伝わること。2026-10-18改訂。STEP2の「動画尺」参照）。

```bash
python3 kl_video_gen.py --episode kl{NNN}
```

引数なしで本編（`kl{NNN}.mp4`）とShorts（`kl{NNN}_shorts.mp4`）の両方が
生成される（Shortsのみ再生成したい場合は `--shorts-only`、本編のみは
`--no-shorts`）。

**掛け合い形式:** 字幕・二人の立ち絵（話している方が明るく大きい）・名札（名前＋肩書き）・判定ラベルを、
1本の透明な重ね合わせ動画にして重ねる（`kl_dialogue.build_overlay_track`）。確認では、話者と明るい
立ち絵が一致しているか、判定ラベルが `verdict_from_line` の行で出るか、`check` のグラフのラベルが立ち絵に
隠れていないかも見る。

**立ち絵の動画化（2026-10-17〜、パイロット）:** `assets/cast/video/{role}_{expr}.webm` がある表情は、立ち絵が
待機ループの動画（息づかい・まばたき）になる（`kl_dialogue.build_sprite_tracks`。無い表情は静止画のまま、混在可）。
このときは「背景 → 字幕帯 → 大輔 → 沙織 → 字幕・名札・判定ラベル等」の順に重ねる。確認では上の項目に加えて、
(a) 表情の切り替えでちらつき・位置ずれが無いか、(b) 立ち絵の縁にピンクのにじみが無いか、(c) 手のポーズが崩れて
いないか（Veo の動画は6秒の後半で手が下がるため前半だけを使っている）を、本編・Shortsのフレームで見る。
不具合があれば `--static-cast`（または `KL_STATIC_CAST=1`）で従来の静止画に戻して作り直してよい。表情を足した・
`cast.json` の表情の説明を変えたときは、`kl_cast_gen.py`（静止画）に加えて `kl_cast_video.py gen`→`post` で
動画も作り直す（gen は課金。作るまでは静止画で出る）。サムネイルは静止画の立ち絵のまま。
**口パク（2026-10-17〜）:** 話している間だけ `{role}_{expr}_talk.webm` の「話しているループ」に切り替わる。確認では、台詞の間だけ口が
動き、聞いている側・台詞の合間は口が閉じた待機ループになっているかを見る。不具合があれば `--no-talk`（`KL_NO_TALK=1`）で待機ループだけに戻せる。
確認用に先頭だけ出すときは `--limit-seconds 90 --out ~/Desktop/kl_cast_video_proto/...`（本番の出力を上書きしない）。

**自己紹介カード（2026-10-05〜）:** ティザーの直後、本編の最初のシーンの頭に、二人の自己紹介の吹き出し
（`cast.json` の `intro`）と二人の関係の一文（`relationship`）を出す。初めて見た人が「この二人は誰？」とならないため
（なるさんの指示）。**大輔の吹き出しを0〜4秒、沙織の吹き出しを3〜7秒（1秒重なる）の順に出す**（`kl_dialogue.INTRO_*`）。
**台詞は吹き出しと関係なく、最初のシーンの頭から始まる**（無音の間は作らない。吹き出しは台詞・字幕に重ねて出る）。
冒頭の離脱が気になる回は、エピソードJSONの `"intro_card": false` で外せる。効果は `/kl-analytics` で本編の
30秒時点の維持を見て判断する。名札の肩書き（`role_short`）は常に出る。

完成後、複数箇所（本編: ティザー・本編冒頭・本編中盤・
ロゴアウトロ、Shorts: 冒頭・中盤・末尾）をフレーム抽出して目視確認し、
STEP9に記載のテロップ不具合（単語途中分割・一瞬で消えるカード・シーン境界の
重複）がないかも合わせて確認する。`SendUserFile` でユーザーに送る。
フィードバックがあれば該当工程（画像/音声/テロップ/動画生成）に戻って修正し、
**修正後は必ず `kl_finalize.py` でGoogle Driveへ同期してから
`kl_video_gen.py` を再実行する**（`kl_video_gen.py`はGoogle Drive側の素材を
読むため、Desktop側の修正だけでは反映されない。kl001制作時に実際にこれが
原因で修正が反映されない事故が起きている）。

**テロップの描画設定（フォント・縁取り太さ・色等）は `kl_telop_gen.py` と
`kl_video_gen.py` の両方に別々の実装があり、片方だけ直すと反映漏れが起きる
（kl001制作時に実際に発生）。テロップの見た目を変更する際は両ファイルを
同時に修正すること。**

**動画の確認が済んだら、`kl_finalize.py` を再実行して完成動画をGoogle Driveへ
同期する（2026-08-30追加）:**

```bash
python3 kl_finalize.py --episode kl{NNN}
```

**このSTEPの実行を忘れないこと。** `kl_video_gen.py`の出力
（`~/Desktop/kagaku-life/output/kl{NNN}.mp4`・`kl{NNN}_shorts.mp4`）は
ローカルのDesktopに書き出されるだけで、STEP11で行ったDrive同期には含まれて
いない（STEP11時点ではまだ動画ファイルが存在しないため）。`/kl-upload`
（`kl_sns_up.py`）はGoogle Drive `Kagaku-Life/KL{NNN}/output/`から動画を
読むため、ここでfinalizeを再実行しておかないと、後日`/kl-upload`実行時に
「本編動画が見つかりません」で失敗し、その場で`kl_finalize.py`を慌てて
再実行する羽目になる（kl007・kl008で実際に2回連続発生した）。
